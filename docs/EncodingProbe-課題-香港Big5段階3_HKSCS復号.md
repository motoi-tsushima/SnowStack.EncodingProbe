## 0. 決定

**本製品（EncodingProbe）では対応しない。**

私用領域の内容に干渉しないことが本製品の基本方針である（私用領域方針 1 章・5 章）。
HKSCS 固有字は私用領域の符号位置として利用者に渡し、その解釈（HKSCS の字として読むかどうか）は利用者に任せる。
私用領域方針 6.1 の方法（利用者が保有する対応表による写し替え）で、利用者側で対処できる。

仮に何らかの対処を提供する場合も、本製品の機能としてではなく、**別製品または別機能**として扱う。

以下の 1〜5 章は起票時の検討内容であり、記録として残す。
別製品・別機能として検討する際の出発点として使える。

## 1. 現状（1.2.0 第二次修正の時点）

- 香港の Big5 は、HKSCS 固有字を含んでいても `950 / big5` と判定する
- .NET には HKSCS のデコーダーが無い。`Encoding.GetEncoding(951)` は PS 5.1 / 7.x とも失敗し、
  `Encoding.GetEncoding("big5-hkscs")` は 950 を返す
- そのため HKSCS 固有字は、例外も置換文字も出さずに私用領域（U+E000–U+F8FF）へ写される
  （`88 62` → U+F325、`8B F8` → U+F570、`FA 5F` → U+E01F、`FE 52` → U+E286。実測、PS 5.1 / 7.x 同一）
- 私用領域方針により、本処理はこれに介入しない。加工せずに書き戻せばバイト列は保存される
  （`PrivateUseAreaRoundTripTests`、PSCompat の `HongKong/hkscs/往復` が固定している）

つまり現状は「壊さずに運べるが、意味としては読めない」。

## 2. 課題

香港のファイルを `Get-ProbedContent` で読んだとき、HKSCS 固有字を本来の Unicode の文字として得たい、
という要求に応えるかどうか。

## 3. 前提となる制約（私用領域方針より）

- **既定の動作は変えない。** 写像を提供する場合は明示指定によるオプトインとする（私用領域方針 7 章）
- 私用領域の符号位置の意味は環境ごとに異なる（HKSCS・Big5-UAO・倚天拡張・造字）。
  バイト列の出現から HKSCS と断定はできない（報告書 3 節）
- 写し替えは一方向である。HKSCS として復号した文字列を cp950 へ書き戻しても元のバイト列にはならない
  （私用領域方針 6.2）。符号化側も HKSCS として実装しない限り往復は成立しない
- コードページ 951 を判定結果として返してはいけない（報告書 4 節。読めていたファイルが読めなくなる）

## 4. 検討すべきこと

1. **対応表の出所と再配布条件。** HKSCS-2016 の対応表（約 5,000 字規模）の入手元とライセンス。
   WHATWG Encoding Standard の `index-big5` を使う場合の条件。
   `THIRD-PARTY-NOTICES.txt` と `EncodingProbe.License` への記載
2. **提供の形。** 次のどれにするか
   - `System.Text.Encoding` 派生クラス（復号・符号化の両方）を公開 API として追加する
   - 復号後の文字列に対する写し替え関数だけを提供する（私用領域方針 6.1 の `$gaiji` を同梱する形）
   - PowerShell の統一語彙に `big5-hkscs` を独自に追加する（.NET の `big5-hkscs` = 950 と意味が衝突する）
3. **オプトインの指定方法。** `-Encoding big5-hkscs` のような語彙か、別のスイッチか。
   判定（`-Encoding Auto`）の結果として自動で HKSCS を選ぶことはしない（既定の動作を変えないため）
4. **符号化の扱い。** HKSCS に無い文字、および HKSCS が Unicode の結合文字列に写す字（一部の字は 2 符号位置になる）の扱い
5. **両 TFM・両ホストでの一致。** net48 / net10.0、PS 5.1 / 7.x で同一の結果になることの検証（PSCompat）
6. **段階 2（`EncodingWebName = big5-hkscs`）との関係。** 第二次修正では見送った。
   段階 3 を実装する場合に、判定結果の名前をどうするかを合わせて決める
