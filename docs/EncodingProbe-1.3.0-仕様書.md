### 1.5 基本方針

1. **CSV の読み書きの規則は、Windows PowerShell 5.1 でも PowerShell 7.x の動作に合わせる。** 両ホストで、同じ入力から同じ結果（読み込みは同じオブジェクト、書き出しは同じバイト列）を得る
   （日付・数値の書式は現在のカルチャーとホストの .NET（5.1 は NLS、7.x は ICU）で決まるため、ko-KR・zh-TW・zh-HK・ar-SA などのカルチャーでは両ホストで違うことがある。17 章。BUG-0005。
   `-UseCulture` の区切り文字も同じで、ms-ID・fa-AF・es-BZ など 36 のカルチャーでは両ホストで違う。17 章。BUG-0029）
2. **標準コマンドの明らかな欠陥は直す。** 本モジュールは、標準コマンドの欠陥を補うためのものである。直した点は、標準との差異として一覧にする（13 章、21 章）
3. **文字を黙って失わない。** 判定を誤った可能性がある場合は、処理する前に止める（4 章）
4. RFC 4180 と PowerShell の標準の挙動が食い違う場合は、PowerShell の標準に合わせる（例: 改行は CR-LF 固定ではなく OS の既定）

# 第 1 部 共通の部品

## 2. 先頭 N 行の切り出し

### 2.1 目的

巨大なファイルの判定を、先頭の N 行だけで行う。バイト数ではなく行数で切るのは、切った末尾が必ず改行になり、
多バイト文字の途中で切れることがないためである。判定処理（クラスライブラリ）を変更せずに済む。

`Resolve-Encoding` / `Import-ProbedCsv` / `Export-ProbedCsv` の `-DetectionLineCount` は、**すべてこの部品を使う**。
同じファイルと同じ N に対して、3 つのコマンドの判定結果は常に一致する（3.3）。

### 2.2 N の意味

- N は**物理的な行数**である。改行（CR-LF / LF / CR）で区切られた単位を 1 行と数える
- CR-LF は 1 個の改行として数える
- CSV の引用符の中にある改行も 1 行と数える。**N は CSV のレコード数ではない**（ヘルプに明記する）
- U+2028 / U+2029 / U+0085 は改行として数えない（`LineBreakResolver.Normalize` と同じ）

### 2.3 改行の型

ファイルの符号化単位によって、改行のバイト列が異なる。次の 5 つの型を区別する。

| 型 | 単位 | LF | CR | 位置の条件（ファイル先頭からのオフセット。BOM を含む） |
|---|---|---|---|---|
| 1 バイト | 1 | `0A` | `0D` | なし |
| UTF-16LE | 2 | `0A 00` | `0D 00` | 先頭のバイトが偶数の位置 |
| UTF-16BE | 2 | `00 0A` | `00 0D` | 先頭のバイトが偶数の位置 |
| UTF-32LE | 4 | `0A 00 00 00` | `0D 00 00 00` | 先頭のバイトが 4 の倍数の位置 |
| UTF-32BE | 4 | `00 00 00 0A` | `00 00 00 0D` | 先頭のバイトが 4 の倍数の位置 |

「1 バイト」の型は、ASCII 互換のすべての文字エンコーディング（UTF-8、Shift_JIS、EUC 系、GBK / GB18030、Big5、UHC、
ISO-2022 系、シングルバイト系）に当てはまる。これらは多バイト文字の 2 バイト目以降に `0A` / `0D` が現れない。

### 2.4 型の決定

次の順に決める（第五次で 2・3 を改めた。規則と値の根拠は `docs/EncodingProbe-1.3.0-調査-切り出しの境目.md` の 1・5・10・11 章）。

1. **BOM がある場合は、BOM から型を決める。** UTF-8 の BOM は「1 バイト」、UTF-16 / UTF-32 の BOM はそれぞれの型とする。
   BOM の判定は `ByteOrderMarkDetection` と同じ規則による（UTF-32LE の BOM `FF FE 00 00` を UTF-16LE と取り違えないこと）
2. **BOM が無い場合は、先頭の探索範囲を単位に区切って数え、次の規則で型を決める。** 探索範囲は先頭の 64 KiB（ファイルがそれより短ければ全体）とし、
   オフセット 0 から UTF-16 は 2 バイト、UTF-32 は 4 バイトずつ区切る（端数のバイトは数えない）。型ごとに数える値は次のとおり。

   | 値 | UTF-16LE（BE は A と B が入れ替わる） | UTF-32LE（BE はバイトの順を逆にしたもの） |
   |---|---|---|
   | N | 全単位数 | 全単位数 |
   | A（その型の英数字の形） | `<00 以外> 00` | 上位の 2 バイトが `00` で、下位の 2 バイトが両方 `00` ではない |
   | B（逆のバイト順の英数字の形） | `00 <00 以外>` | 下位の 2 バイトが `00` で、上位の 2 バイトが両方 `00` ではない |
   | Z | 2 バイトとも `00` | 4 バイトとも `00` |
   | Abr（A のうち改行の形） | `0A 00` / `0D 00` | （使わない） |
   | P（UTF-16 だけ） | 両方のバイトが `0x20`〜`0x7E` の単位 | （使わない） |

   次の順に調べ、最初に成り立った型にする。どれも成り立たなければ「1 バイト」の型とする。

   > 共通の条件（型ごと）: **A ≥ min(16, ⌈0.6 × N⌉)** かつ **Z = 0**。UTF-16 の型ではさらに **P ≤ 0.7 × N**
   >
   > 1. UTF-32LE → UTF-32BE: 共通の条件 かつ **B ≤ 0.2 × A**
   > 2. UTF-16LE → UTF-16BE: 共通の条件 かつ **改行の向きが合う**（Abr ≥ 4 かつ 逆のバイト順の Abr ≤ 0.25 × Abr）
   > 3. UTF-16LE → UTF-16BE: 共通の条件 かつ **B ≤ 0.2 × A**

   - **手当て:** 規則で「1 バイト」の型になり、探索範囲に `0x00` があり、しかもファイル全体が 64 KiB 以内のときは、
     行で切らずに**ファイル全体を切り出す**（改行が無い場合と同じ扱い。2.6）。短い日本語だけの UTF-16 は A が少なく 1 バイトの型になるが、
     1 バイトの型として最初の `0A` で切ると、切り出しが文字の途中で終わって Shift_JIS などと判定され、全体の検証も通って黙って化けるため（調査文書 11.4 節）
   - 比は整数で比べる（⌈0.6 × N⌉ = ⌊(3N + 4) / 5⌋ など）。調査の 1033 件で、決まる型が調査の規則のモデルと一致することをテストで確かめている
3. **決めた型の改行だけを、先頭から探す。** 見つかった `0A` / `0D` のうち、決めた型の**バイト列と位置の条件の両方**（2.3 の表）に一致するものを改行とする。
   ほかの型の改行の形は見ない（例: UTF-16LE の「上」U+4E0A は `0A 4E` であり、改行ではない。UTF-16BE の U+0D00 `0D 00` は UTF-16LE の CR の形だが、UTF-16BE と決めたので改行ではない）
4. ファイルの末尾まで改行が見つからなかった場合は、改行が無いとみなし、2.6 に従う

> **経緯（第五次）:** 第四次までは、2 で「`0x00` があれば 1 バイトの型を候補から外す」とし、3 で「候補の型のうち最初に改行の形に一致した型」に決めていた。
> この規則は `0x00` を含む ASCII の CSV（`00` で埋めた固定長レコード、行末の `00`）を UTF-16 と決め（BUG-0002）、
> 最初の改行より前に U+0D00 / U+0A00 がある BOM 無しの UTF-16 を逆のバイト順と決めていた（BUG-0013）。
> どちらも全体の検証を通ってしまい、黙って化ける・追記でファイルを壊すことがあった。

**既知の限界（第五次。調査文書 6 章・10.4 節・11 章）。** 次の入力は、規則で型を誤るか決められない。

| 入力 | 結果 |
|---|---|
| U+0D00 / U+0A00 が文字の 10% 以上を占める BOM 無しの UTF-16 | 逆のバイト順になることがある。全体で判定しても誤る既存の限界でもある（1% までなら正しく分かれる） |
| 先頭 64 KiB に英数字も改行も無い BOM 無しの UTF-16（日本語だけの 1 行が 64 KiB を超えるもの） | バイト順を誤る。ただし誤った型の改行の形も 64 KiB の中には無いので、64 KiB の中では切らない |
| 平仮名だけの BOM 無しの UTF-16（P/N が 0.7 を超える） | 「1 バイト」の型になる |
| 各行に `00` が 1 つあり、本文が Shift_JIS・EUC-JP・UTF-8 の日本語など `0x80` 以上のバイトを多く使う 1 バイトのファイル（16 行以上で、行の長さがすべて偶数か、`00` が改行の隣にあるもの） | UTF-16 の型になる。`Import-` / `Export-ProbedCsv` は正しく読むか、4 章の検証で止まる（調査文書 10.4・11.2 節） |
| U+0000 を含む BOM 無しの UTF-16 / UTF-32 | Z = 0 を満たさず「1 バイト」の型になる（追補 4.3 の U+0000 の限界と同じ入力） |
| `00` を含む 64 KiB 以内の 1 バイトのファイル | 2 の手当てにより、`-DetectionLineCount` を指定してもファイル全体で判定する |
| 1 バイトの文章に、離れた `00` が 16〜50 個程度ある 64 KiB を超えるファイル | 偶然 UTF-16 の形にそろうと UTF-16 の型になる（確率は 0.3% 以下。調査文書 5.1 節） |

### 2.5 行の数え方と切る位置

型が決まったら、**ファイルの先頭から**その型の単位で改行を数え、N 個目の改行の直後で切る。

- 単位の境界（2.3 の位置の条件）に合わない `0A` / `0D` は改行と数えない
- CR の直後に LF が続く場合は、合わせて 1 個の改行とする。**CR と LF の間で切らない。** CR がバッファの末尾に来た場合は、次の単位を読んでから決める
- 切り出したバイト列は、BOM を含むファイルの先頭から、N 個目の改行（CR-LF なら LF まで）の末尾までとする
- 切り出したバイト列の長さは、UTF-16 なら 2 の倍数、UTF-32 なら 4 の倍数になる（`Utf16_Detection` / `Utf32_Detection` は、長さが単位の倍数でないと対象外とするため、これが必要である）

### 2.6 N 行に満たない場合・改行が無い場合・上限

- ファイルの改行が N 個未満の場合は、ファイル全体を切り出す。結果は、全体で判定した場合と同じになる
- 改行が見つからない場合（2.4 の 4）も、ファイル全体を切り出す
- 切り出すバイト列の大きさが `EncodingInheritance.MaxDetectableLength` を超える場合は、判定できないエラーとする（全体の判定と同じ扱い・同じ ID）。
  改行の無い巨大なファイル（1 行に詰めた JSON など）では、`-DetectionLineCount` を指定しても判定できない。ヘルプに記載する
- 0 バイトのファイルは、既存の規則（全体の判定）と同じに扱う

### 2.7 判定への受け渡し

切り出したバイト列を `EncodingProbe.Detect(byte[], EncodingDetectorOptions)` に渡す。
`-Culture` / `-Strategy` は全体の判定と同じく `EncodingDetectorOptions` に入れる。

## 3. 先頭 N 行の判定結果の扱い

### 3.1 `Resolve-Encoding`

判定結果（`EncodingInformation`）を**そのまま**出力する。読み替え（3.2）も検証（4 章）も行わない。
`Resolve-Encoding -DetectionLineCount` は「先頭 N 行が何に見えるか」を報告するコマンドである。
`us-ascii` と報告する場合は、`LineBreak` も `us-ascii`（1 バイト単位）として数えた値である。3.2 のように UTF-16 / UTF-32 に読み替えて数え直すことはしない
（1.3.0 第五次の後半で利用者が決定。`us-ascii` と報告する以上、改行も `us-ascii` として数える。ヘルプに書いた）。

### 3.2 `Import-ProbedCsv` / `Export-ProbedCsv`

判定結果を使う前に、次の読み替えを行う。読み替えには、切り出しで決めた改行の型（2.4）を使う。

| 判定結果 | 切り出しで決めた改行の型 | 読み替え後 |
|---|---|---|
| `20127 / us-ascii`（先頭 N 行のバイトがすべて `0x80` 未満だった） | 1 バイト、または改行が無い | **BOM 無しの UTF-8（65001）** |
| 同上 | UTF-16LE / UTF-16BE | BOM 無しの UTF-16LE（1200）/ UTF-16BE（1201） |
| 同上 | UTF-32LE / UTF-32BE | BOM 無しの UTF-32LE（12000）/ UTF-32BE（12001） |
| それ以外 | — | そのまま |

ASCII は UTF-8 の部分集合であり、ファイルが本当に UTF-8 なら必ず正しく読める。
UTF-8 でなければ、4 章の検証で止まる（黙って文字化けすることはない）。

UTF-16 / UTF-32 の行が必要な理由: 英数字だけの BOM 無し UTF-16 / UTF-32 は、判定処理が UTF-16 / UTF-32 と判定する（追補 2 章）。
しかし、2 バイトとも `0x80` 未満になる文字（「上」U+4E0A = UTF-16LE で `0A 4E`、「字」U+5B57、「あ」U+3042 など）が英数字に混じった
BOM 無しの UTF-16 / UTF-32 は、すべてのバイトが `0x80` 未満で、かつ追補 2.2 の形にも合わないため、`us-ascii` と判定される（追補 4.1。既知の限界）。
これを UTF-8 と読み替えると、UTF-8 の検証を通ってしまい（`0x00` も ASCII も UTF-8 として正しい）、`U+0000` が混じった文字列として読まれる。
切り出しの段階で改行の型が分かっているので、それに従って読み替える（24 章 U4）。

> **経緯:** 当初は、判定処理が `0x00` を含む ASCII をすべて ASCII と判定するため、英数字だけの BOM 無し UTF-16 / UTF-32 を救う目的でこの行を設けた。
> 追補で判定処理を直した後は、英数字だけのものは判定の時点で UTF-16 / UTF-32 になり、この行を通らない。追補 4.1 の入力のために残す（追補 1 章）。

- この読み替えは `-DetectionLineCount` を指定した場合だけ行う。全体で判定した場合は、既存の規則どおりそのまま使う
- **UTF-16 / UTF-32 に読み替えた場合は、改行の種類（`LineBreak`）も、読み替えた後の単位で切り出したバイト列を数え直す**（第五次で改めた）。
  判定処理は先頭 N 行を us-ascii として 1 バイトずつ数えるので、「上」（`0A 4E`）を LF と数え、改行が CR のファイルを `LfAndCr` と報告していた。
  追記の改行はこの値から決まるため、CR のファイルに LF を追記していた（BUG-0014）
  > **経緯:** 第四次までは「改行の型（`LineBreak`）は読み替えない」としていた。誤りだったので改めた
- **us-ascii を UTF-8 に読み替えた場合は、4 章の検証で ISO-2022 のエスケープシーケンスも探す**（第五次。4.3）。
  ISO-2022-JP / KR / CN のバイト列はすべて `0x80` 未満なので、先頭 N 行が英数字だけだと UTF-8 の検証を必ず通ってしまう（BUG-0009）
- `Resolve-Encoding` は読み替えない（3.1）。先頭 N 行が追補 4.1 の入力（2 バイトとも `0x80` 未満の文字を含む BOM 無しの UTF-16 / UTF-32）であれば `us-ascii` を報告する。
  英数字だけの BOM 無し UTF-16 / UTF-32 には、その文字エンコーディングを報告する（追補 5 章）

### 3.3 一致の保証

同じファイル・同じ N・同じ `-Culture` / `-Strategy` に対して、
`Resolve-Encoding -DetectionLineCount N` が返す `EncodingInformation` と、
`Import-ProbedCsv` / `Export-ProbedCsv` が 3.2 の読み替えの**前**に得る `EncodingInformation` は、すべてのプロパティで一致する。
自動テストでこれを確認する。

## 4. 全体の厳密な検証

### 4.1 適用範囲

`-DetectionLineCount` を指定して判定した結果を使う場合は、**使う前に必ず、そのファイルの全体を厳密に復号して検証する。**

| コマンド | 検証するファイル |
|---|---|
| `Import-ProbedCsv` | 読み込むファイル |
| `Export-ProbedCsv` | `-Append` の追記先、明示的な `-Encoding Auto` の出力先、`-EncodingFrom` の参照ファイル（24 章 U2） |
| `Resolve-Encoding` | 検証しない（3.1） |

- 全体で判定した場合は検証しない（1.4）
- `-Encoding` で文字エンコーディングを明示した場合は、判定も検証も行わない
- BOM で文字エンコーディングが決まった場合も検証する（例外を設けない）

### 4.2 方法

- `EncodingVocabulary.BuildStrictEncoding(codePage)`（例外フォールバック）で `Decoder` を作る
- ファイルを固定サイズのバッファ（64 KiB）で先頭から順に読み、`Decoder.GetChars(..., flush: false)` に与える。復号した文字は使わずに捨てる
- 最後に `flush: true` で呼び、末尾で途切れた多バイト文字も検出する
- BOM はスキップしてから復号する（BOM の長さは `ProbedFileReader` と同じ規則で求める）
- ファイルは `FileShare.ReadWrite`、`FileOptions.SequentialScan` で開く（`ProbedFileReader` と同じ）

**メモリの使用量は、ファイルの大きさに関係なく一定である**（バッファ・文字バッファ・`Decoder` 1 個）。
`Decoder` は、バッファの境目で分かれた多バイト文字を内部の状態で正しくつなぐ。

### 4.3 失敗した場合

- `Import-ProbedCsv`: そのファイルのレコードを**1 件も出力せずに**、非終了エラーとする。次のファイルに進む
- `Export-ProbedCsv`: ファイルに**何も書かずに**、終了エラーとする
- エラー ID は `DetectionVerificationFailed` とする（新設）
- メッセージには、次を含める
  - ファイルのパス
  - 先頭 N 行の判定で決めた文字エンコーディング（統一語彙名）と N
  - 最初の不正なバイト列の位置（ファイル先頭からのバイトオフセット）とそのバイト列（`Convert-ProbedContent` の `InvalidByteSequence` と同じ形式）
  - 対処の案内: `-DetectionLineCount` を増やすか、`-Encoding` で文字エンコーディングを指定する
- 不正な位置は `DecoderFallbackException.Index` を使わずに求める（.NET Framework と .NET Core で基準が違い、5.1 と 7.x で異なる値を報告するため。1.2.0 で判明済み）。
  `ConvertProbedContentCommand.FindInvalidBytes` と同じ考え方で、失敗したときだけ、失敗したバッファの付近を 1 バイトずつ再走査してよい。
  **5.1 と 7.x で同じ位置を報告すること**
- **us-ascii を UTF-8 に読み替えた場合（3.2）は、同じ走査の中で、ESC（`0x1B`）の直後が `$`（`0x24`）・`(`（`0x28`）・`)`（`0x29`）のバイト列も探す。**
  見つかれば、同じ ID `DetectionVerificationFailed` で失敗とする（第五次。BUG-0009）。メッセージには、ESC の位置とその 2 バイト、
  先頭 N 行が英数字だけだったので UTF-8 として読んだこと、対処の案内（`-DetectionLineCount` を外すか、エスケープシーケンスのある行まで増やす）を含める。
  端末の制御文字を記録したログ（`ESC ( B` など）も止まるが、判定を誤ったまま処理するより安全な側に倒す。`ESC [` などは止めない

### 4.4 時間とファイルの読み込み回数

`-DetectionLineCount` を指定すると、ファイル全体を 2 回読む（検証と、本来の処理）。巨大なファイルほど時間がかかる。
これは「判定を誤ったまま処理しない」保証の代償である。速さが必要な場合は `-Encoding` で明示すれば判定も検証も行わない。ヘルプに記載する。

`-DetectionLineCount` を指定した場合の処理の順序:

| 段階 | 読む範囲 | メモリ |
|---|---|---|
| ① 判定 | 先頭 N 行（2 章） | N 行分 |
| ② 検証 | 全体（ストリーム） | 一定 |
| ③ 本来の処理（インポート、追記先のヘッダーの読み取り） | 全体または先頭（ストリーム） | 1 レコード分 |

# 第 2 部 `Resolve-Encoding -DetectionLineCount`

## 6. 仕様

### 6.1 パラメータ

| パラメータ | 型 | パラメータセット | 検証 | 説明 |
|---|---|---|---|---|
| `-DetectionLineCount` | `long`（`Int64`） | `Default` | `ValidateRange(1, long.MaxValue)` | 判定に使う先頭の行数。省略時はファイル全体で判定する（従来どおり） |

- 位置パラメータにしない。パイプラインから受け取らない
- 0 と負の値はパラメータ束縛の段階で拒否する（0 行の判定には意味がない。`Get-ProbedContent -TotalCount` の 0 とは扱いが違う）
- 名前は `-TotalCount` にしない。`Get-Content` / `Get-ProbedContent` の `-TotalCount` は「出力する行数」であり、意味が違うため。
  1.4.0 で `Get-ProbedContent` に判定の行数を加えるときに、同じコマンドに `-TotalCount` と `-DetectionLineCount` が並ぶことを想定している。別名も設けない

### 6.2 挙動

- `-DetectionLineCount` を指定した場合は、2 章の切り出しを行い、切り出したバイト列を判定して、結果をそのまま出力する（3.1）
- 出力する `EncodingInformation` の `LineBreak` も、切り出した範囲だけで判定した結果になる（後半だけ改行が混在するファイルは見逃す）
- 切り出しが判定の上限を超えた場合（2.6）は、終了エラーとする。既存の「ファイルが無い」と同じく終了エラーで、ID は全体の判定の上限超過と同じものを使う

### 6.3 ヘルプ

5 言語の MAML に `-DetectionLineCount` を追加し、次を記載する。

- 行数は物理的な行数であり、改行（CR-LF / LF / CR）で数える。CSV のレコード数ではない
- 結果は先頭 N 行だけを見たものであり、後半にだけ現れる文字（ASCII の後の日本語など）は反映されない。
  先頭 N 行が ASCII だけなら `us-ascii` と報告する（BOM 無しの UTF-16 / UTF-32 で、先頭 N 行に 2 バイトとも `0x80` 未満になる文字（「上」など）が英数字に混じる場合も `us-ascii` になる。追補 4.1。
  英数字だけの BOM 無し UTF-16 / UTF-32 は、その文字エンコーディングと報告する）
- NOTES に、追補 4 章の既知の限界（3 点）を記載する（追補で追加）
- `LineBreak` も先頭 N 行だけで判定した結果である
- 改行の無いファイルでは、ファイル全体を読む（大きすぎる場合は判定できない）

# 第 3 部 `Import-ProbedCsv`

## 7. 基本方針

`Import-ProbedCsv` は、文字エンコーディングを判定して CSV ファイルを読み込み、各レコードをオブジェクトとして出力する。

- **解析は、PowerShell 7.x の `Import-Csv` から移植した処理で行う**（5 章）。ホストの `Import-Csv` は呼ばない。
  そのため、Windows PowerShell 5.1 でも 7.x の `Import-Csv` と同じ結果になる
- 1 レコードずつ出力する（ストリーミング）。ファイル全体をメモリに読まない（全体で判定する場合の判定処理を除く）
- 標準の `Import-Csv` との差異は 13 章に一覧する

> **ホストの `Import-Csv` に任せない理由（実測報告 3 章）:** Windows PowerShell 5.1 の `Import-Csv` は、CR だけの改行の CSV を読むと
> エラーも警告も出さずに 0 件を返す（データが黙って失われる）。W3C 拡張ログ形式にも対応していない。
> また 5.1 の `-Encoding` は列挙型で、EUC-JP などを渡せない。

## 8. パラメータ一覧

パラメータセットは 4 つ。`DelimiterPath`（既定）、`DelimiterLiteralPath`、`CulturePath`、`CultureLiteralPath`（標準の `Import-Csv` と同じ構成）。

| パラメータ | 型 | 位置 | パイプライン | 別名 | 説明 |
|---|---|---|---|---|---|
| `-Path` | `string[]` | 0 | ByValue, ByPropertyName | 9.1 | 読み込むファイル。ワイルドカード対応。`*Path` セットで必須 |
| `-LiteralPath` | `string[]` | — | ByPropertyName | `PSPath`, `LP` | ワイルドカード非対応。`*LiteralPath` セットで必須 |
| `-Delimiter` | `char` | 1 | — | — | 区切り文字。`Delimiter*` セット。省略時は `,` |
| `-UseCulture` | switch | — | — | — | 区切り文字に、現在のカルチャーのリスト区切り文字を使う。`Culture*` セットで必須 |
| `-Header` | `string[]` | — | — | — | 列名。指定すると、ファイルの 1 行目もデータとして読む（標準と同じ） |
| `-Encoding` | 多形（読み取り用） | — | — | — | 統一語彙ほか。既定は `Auto`（判定する）。`Get-ProbedContent -Encoding` と同じ語彙と規則 |
| `-DetectionLineCount` | `long` | — | — | — | 判定に使う先頭の行数。`ValidateRange(1, long.MaxValue)`。省略時は全体で判定する |
| `-Culture` | `string` | — | — | — | 判定に用いるカルチャー名（`Resolve-Encoding` と同じ） |
| `-Strategy` | `string` | — | — | — | 判定方式（`Resolve-Encoding` と同じ） |

- **`-Culture` と `-UseCulture` は別のものである。** `-Culture` は文字エンコーディングの判定に使うカルチャー、`-UseCulture` は区切り文字の決め方である。
  両方を同時に指定できる。ヘルプの両パラメータの説明に、この違いを明記する
- `-Encoding` を明示した場合（`Auto` 以外）、`-DetectionLineCount` / `-Culture` / `-Strategy` は判定を行わないため意味を持たない。
  既存の Probed 系コマンドが `-Encoding` 明示時の `-Culture` / `-Strategy` を扱うのと同じ扱いにする（警告もエラーも出さない）

## 9. パスの解決と複数のファイル

### 9.1 パスの解決

- `Get-ProbedContent` と同じ部品（`ProbedContentCommandBase` のパスの解決）と同じ規則を使う
- `-Path` のワイルドカードが**複数のファイルに一致した場合は、一致したファイルを順に読む**（標準の `Import-Csv` はエラーになる。実測報告 M2）
- `-Path` / `-LiteralPath` に配列を渡した場合は、順に読む
- `Get-ChildItem | Import-ProbedCsv` は **両ホストで**読めること（標準の 5.1 は `CannotSpecifyPathAndLiteralPath` で失敗する。実測報告 M2）。
  パイプライン束縛の属性（別名を含む）は、両ホストで同じ形が動作確認済みの `Get-ProbedContent` に合わせる
- 存在しないファイル、フォルダーを指定した場合は、`Get-ProbedContent` と同じ非終了エラー（同じ ID）とし、次のパスに進む
- ワイルドカードが 0 件に一致した場合は、`Get-ProbedContent` と同じく、エラーを出さずに何も読まない（標準の `Import-Csv` は終了エラー）
- **パイプラインから渡したファイル（FileInfo）は `-LiteralPath` に束縛する**（1.3.0 第五次の後半。BUG-0003）。別名 `FullName` を `-Path` から `-LiteralPath` に移し、
  `-LiteralPath` の別名は `PSPath`・`LP`・`FullName` とした（`Get-ProbedContent`・`Set-ProbedContent`・`Add-ProbedContent`・`Convert-ProbedContent` も同じ）。
  これまでは `FullName` が `-Path` に束縛されてワイルドカードとして展開され、`a[1].csv` を流すと `a1.csv` を読んでいた。文字列をパイプラインで渡した場合は、これまでどおり `-Path`（ワイルドカード）

> **改めた経緯（2026-10-19、第二次）:** 当初は「ワイルドカードが 0 件」も非終了エラーとしていた。実装時に確かめたところ、
> 既存の `Get-ProbedContent` は両ホストとも 0 件のワイルドカードでエラーを出さなかった（パスの解決の部品を共用している）。
> 既存のコマンドの挙動は変えないため、利用者の決定で `Get-ProbedContent` に合わせた（実装記録 6 章）。

### 9.2 複数のファイルを読む場合の規則

- ファイルごとに、文字エンコーディングを判定し（10 章）、ヘッダーを読み直す。ファイルごとに列が違ってもよい（出力されるオブジェクトの形が混ざる）
- `-Header` を指定した場合は、すべてのファイルに同じ列名を使う
- 1 ファイルの失敗（判定の失敗、検証の失敗、ヘッダーの重複、読み取りの失敗）は非終了エラーとし、次のファイルに進む
- 列名が空のときの警告（`H1` などで補う警告）は、標準と同じく、**実行全体で 1 回だけ**出す
- 読み込み中のファイルは `ActiveReadRegistry` に登録する（`Import-ProbedCsv a.csv | Export-ProbedCsv a.csv` を検出するため）

## 10. 文字エンコーディングの決定

| `-Encoding` | `-DetectionLineCount` | 決定方法 | 検証 |
|---|---|---|---|
| 明示（語彙名・WebName・数値・`EncodingInformation`・`Encoding`） | （無視） | その値 | しない |
| `Auto`（既定） | 省略 | ファイル全体で判定する（`ProbedFileReader` と同じ） | しない |
| `Auto`（既定） | 指定 | 先頭 N 行で判定し（2 章）、3.2 の読み替えを行う | **する**（4 章） |

- BOM は、指定にかかわらず常に読み飛ばす（1.1.0 の原則 A。`ProbedFileReader` と同じ）
- 判定に失敗した場合、判定したコードページを実行環境が提供していない場合は、`Get-ProbedContent` と同じ非終了エラー（同じ ID）
- 全体で判定する場合のファイルの大きさの上限は、既存の規則（`MaxDetectableLength`）のとおり。上限を超えた場合のメッセージで、`-DetectionLineCount` を案内する
- 検証を通った後の解析では、検証と同じ厳密な `Encoding` で復号する。解析の途中で復号に失敗した場合（処理中にファイルが書き換えられた場合など）は、
  そこで止めて非終了エラーとする（それまでに出力したレコードは取り消せない）

## 11. 解析

移植した `ImportCsvHelper` のとおりに解析する。主な規則（すべて 7.x の `Import-Csv` と同じ。実測報告 M1 の 7.6.7 の結果と一致すること）:

| 項目 | 規則 |
|---|---|
| 改行 | CR-LF / LF / CR のいずれもレコードの区切りとする（**CR だけの改行も読む**） |
| 引用符の中の改行 | フィールドの一部として、元の改行のまま残す |
| ヘッダーより前の `#` で始まる行 | 読み飛ばす。ただし `#Type`（大文字小文字を区別しない）で始まる最初の行は型名とする |
| ヘッダーより後の `#` で始まる行 | データとして読む |
| `#Fields: ` で始まる行 | W3C 拡張ログ形式のヘッダーとして扱う |
| 型名 | `#TYPE Foo.Bar` なら、出力の `TypeNames` は `Foo.Bar`、`CSV:Foo.Bar` の順（7.x と同じ。5.1 とは順序が逆） |
| 空行 | 読み飛ばす |
| 値の前後の空白 | 移植元のとおり（値の前の空白は除く。引用符の外の後ろの空白は条件により残る） |
| 列より値が多い / 少ない | 多い値は捨てる。足りない列は `$null` |
| ヘッダーの末尾の区切り文字 | 末尾の空の列名は除く |
| 列名が空 | `H1`、`H2`… で補い、警告を出す（実行全体で 1 回） |
| 列名の重複（大文字小文字を区別しない） | そのファイルについてエラー（12 章。24 章 U3）。比べ方は 5.1 でも .NET 10 の `OrdinalIgnoreCase` と同じ（25.3。第六次） |

## 13. 標準の `Import-Csv` との差異

| 項目 | 標準 5.1 | 標準 7.x | `Import-ProbedCsv` | 理由 |
|---|---|---|---|---|
| 文字エンコーディング | `-Encoding` の既定は ANSI（日本語環境では CP932）。列挙型で、EUC-JP などは指定できない | 既定は UTF-8 | 判定する（既定 `Auto`）。統一語彙で指定できる | 本モジュールの目的 |
| CR だけの改行 | **0 件（エラーも警告もない）** | 読める | 読める | データを黙って失わないため（7.x に合わせる） |
| W3C `#Fields:` | 未対応 | 対応 | 対応 | 7.x に合わせる |
| `#TYPE` の型名の順序 | `CSV:Foo.Bar` が先 | `Foo.Bar` が先 | `Foo.Bar` が先 | 7.x に合わせる |
| `Get-ChildItem \| ...` | エラー | 読める | 読める | 7.x に合わせる |
| ワイルドカードが複数に一致 | エラー | エラー | 順に読む | 利便性（Probed 系のコマンドに合わせる） |
| 存在しないファイル | 終了エラー（配列の残りも読まない） | 同左 | 非終了エラー（次のファイルへ進む） | 本モジュールのエラー方針（ファイルごとの失敗は非終了） |
| ワイルドカードが 0 件 | 終了エラー | 同左 | エラーにしない（`Get-ProbedContent` と同じ） | 既存の Probed 系コマンドに合わせる（9.1） |
| 列名の重複 | 終了エラー | 終了エラー | 非終了エラー（24 章 U3） | 同上 |
| `-DetectionLineCount` / `-Culture` / `-Strategy` | 無い | 無い | ある | 本モジュールの追加機能 |

# 第 4 部 `Export-ProbedCsv`

## 14. 基本方針

`Export-ProbedCsv` は、オブジェクトを CSV の行に変換し、文字エンコーディング・BOM・改行を指定してファイルに書き出す。

- **CSV の文字列化は、PowerShell 7.x の `Export-Csv` から移植した処理で行う**（5 章）。ホストの `Export-Csv` / `ConvertTo-Csv` は呼ばない。
  そのため、**両ホストでバイト単位まで同じ CSV になる**（1.2.0 の `Out-ProbedFile` は整形の層をホストに任せたが、`Export-ProbedCsv` は任せない）。
  ただし、日付・数値の書式は現在のカルチャーとホストの .NET で決まり（17 章）、ko-KR・zh-TW・zh-HK・ar-SA などのカルチャーでは両ホストで違うことがある（BUG-0005。標準の `ConvertTo-Csv` も同じ）。
  `-UseCulture` の区切り文字も、ms-ID・fa-AF・es-BZ など 36 のカルチャーでは両ホストで違う（17 章。BUG-0029）
- **符号化の層（文字エンコーディング・BOM・改行・追記・ファイルを開く時点・読み取り専用・`-WhatIf`）は `Out-ProbedFile` の規則に従う**（1.2.0 仕様書 2 章）。
  本書に書いていない点は、1.2.0 仕様書 2 章の該当節のとおりとする
- 書き込み部品（`ProbedFileWriter`・`LineBreakResolver`・`EncodingInheritance`・`ActiveReadRegistry`・`AppendConsistency`・`ReadOnlyAttributeScope`）を共用する
- 出力先は常に 1 件。**失敗はすべて終了エラー**（1.2.0 仕様書 5.1 と同じ基準）
- 標準の `Export-Csv` との差異は 21 章に一覧する

## 15. パラメータ一覧

パラメータセットは 2 つ。`Delimiter`（既定）、`UseCulture`（標準の `Export-Csv` と同じ構成）。
`-Path` / `-LiteralPath` は両方のセットにあり、必須ではない。`BeginProcessing` の最初に「ちょうど一方」を検査し、満たさなければ終了エラー（ID `CannotSpecifyPathAndLiteralPath`。標準と同じ）。

> **改めた経緯（2026-10-19、第三次）:** 当初は `Import-ProbedCsv` と同じ 4 つ（`DelimiterPath` / `DelimiterLiteralPath` / `CulturePath` / `CultureLiteralPath`）としていた。
> 実装したところ、パイプラインから入力を受けて `-LiteralPath` を指定すると、`DelimiterLiteralPath` と `CultureLiteralPath` のどちらか決まらず
> `AmbiguousParameterSet` で失敗した（`Import-ProbedCsv` はパスをパイプラインから受けるのでこの問題が無い）。利用者の決定で、標準の `Export-Csv` と同じ構成に改めた（実装記録 7 章）。

## 16. 文字エンコーディングと改行の決定

### 16.1 文字エンコーディング

1.2.0 仕様書 2.5 の表（`Out-ProbedFile`）と同じ規則とする。要点:

| 指定 | `-Append` なし | `-Append` あり |
|---|---|---|
| 省略 | `utf8NoBOM` | 追記先から継承。追記先が無い、または 0 バイトなら `utf8NoBOM` |
| `Auto` | 出力先の既存ファイルから継承。無ければ終了エラー | 追記先から継承。無ければ終了エラー |
| 明示 | その値 | その値（整合性検査あり） |

`-Encoding` と `-EncodingFrom` の同時指定は終了エラー（1.1.0 と同じ）。

**継承した us-ascii は、BOM 無しの UTF-8 とみなす（第五次）。** 追記先・出力先からの継承（省略・`Auto`）、`-EncodingFrom`、
`-Encoding` に判定結果（`EncodingInformation`）を渡した場合、追記の整合性検査の相手（追記先の文字エンコーディング）が対象で、
書き込みの 4 コマンド（`Set-` / `Add-ProbedContent`、`Out-ProbedFile`、`Export-ProbedCsv`）と `Convert-ProbedContent -EncodingFrom` に共通する。
us-ascii と判定されるのはすべてのバイトが `0x80` 未満のファイルで、それは BOM 無しの UTF-8 としても正しい。`-DetectionLineCount` の読み替え（3.2）と同じ考え方である。
ASCII の文字だけを書く場合のバイト列は変わらない。`-Encoding ascii` の明示は置き換えない。

### 16.2 `-DetectionLineCount` が効く箇所

既存ファイルを判定するすべての箇所に効く。

| 箇所 | 判定する対象 |
|---|---|
| `-EncodingFrom` | 参照ファイル |
| 明示的な `-Encoding Auto` | 出力先の既存ファイル |
| `-Append`（`-Encoding` 省略時の継承、`-Encoding` 明示時の整合性検査の基準） | 追記先の既存ファイル |

`-DetectionLineCount` を指定した場合は、どの箇所でも、先頭 N 行で判定し（2 章）、3.2 の読み替えを行い、**ファイルに書く前に**全体を検証する（4 章）。
検証が失敗したら、何も書かずに終了エラーとする。

> **この規則が必要な理由:** 先頭が英数字だけで後半に日本語がある Shift_JIS の CSV に追記する場合、先頭 N 行の判定では us-ascii となり、
> 3.2 の読み替えで UTF-8 とみなす。検証が無ければ、UTF-8 の行が Shift_JIS のファイルに追記され、二つの文字エンコーディングが混ざる。
> 追記の整合性検査（バイト列の比較）では防げない。比較の基準である追記先の文字エンコーディングそのものを取り違えているからである。

検証は読み取りだけで、ファイルを変更しない。1.2.0 の方針（ファイルを変更しない検査は `ShouldProcess` より前に置く）に従い、
**`ShouldProcess` より前**に行う。`-WhatIf` でも、検証の失敗を同じ ID で報告する。

### 16.3 改行

1.2.0 仕様書 2.6 と同じ。

- `-LineBreak` の明示 → その値
- 参照情報がある（`-EncodingFrom`、明示的な `-Encoding Auto`、`-Encoding <EncodingInformation>`、`-Append` で追記先から継承した場合）→ 参照元の改行（混在は `LineBreakResolver.FromDetected` の規則）
- それ以外 → `Environment.NewLine`（標準の `Export-Csv` と同じく OS の既定。RFC 4180 の CR-LF 固定にはしない）

`-DetectionLineCount` を指定した場合、参照元の改行は先頭 N 行の範囲で判定したものになる。

**`-LineBreak` が決めるのは、各レコード（とヘッダー）の後ろに付ける改行だけである。** 値の中の改行（`"l1`nl2"` など）は置き換えない（標準と同じ）。

### 16.4 表現できない文字（第五次。書き込みの 4 コマンドに共通）

書き込み先の文字エンコーディングで表現できない文字があれば、**そのファイルについてエラー（ID `UnrepresentableCharacter`、`Convert-ProbedContent` と同じ）とし、ファイルは書き込みの前の状態に戻す。**
第四次までは、.NET の既定の置換フォールバックで `?`（`3F`）に、.NET Framework（5.1）ではベストフィット（`é` → `e`）にして黙って書いていた（BUG-0001・0010・0012）。

- 符号化は、コードページから組み立て直した例外フォールバックの Encoding（`EncodingVocabulary.BuildStrictEncoding`）で行う。
  文字エンコーディングを継承した場合・`-Encoding` で明示した場合・`-EncodingFrom` の場合のすべてで同じ。
  `-Encoding` に `System.Text.Encoding` のインスタンスを渡した場合も、そのインスタンスのフォールバックの設定は使わない（BUG-0012）
- メッセージには、最初の表現できない文字の符号位置（`U+XXXX`。補助文字は 1 文字として）・その文字・文字エンコーディングの名前（統一語彙名）・パスを入れる
- 途中まで書いてから気づいた場合も、ファイルを元に戻す。上書き・新規作成は同じフォルダーの一時ファイル（`.~probed<8 桁>.probedtmp`。第六次 B で元の名前を含めない形にした。26.3）に書き、完了したときに置き換える。
  追記は開く前の長さに切り詰める（追記先が無かった場合は作ったファイルを消す）
- 追記の整合性検査（`EncodingChangeOnAppend`）より先に調べる。整合性検査で拒否された場合も、同じくファイルを元に戻す
  （第五次の後半で改めた。前半までは、それまでに書いた行を残していた。1.1.0 仕様書 6.4）
- `Set-` / `Add-ProbedContent` は非終了エラー（ほかのファイルは続ける）、`Out-ProbedFile` / `Export-ProbedCsv` は終了エラー
- 逃げ道のスイッチは設けない（利用者の決定）

### 16.5 上書きの書き方・同じファイルの判定（第五次の後半。書き込みの 4 コマンドと Convert-ProbedContent に共通）

**規則: エラーで止まったら、そのファイルには、その呼び出しで書いた分を残さない。** パイプラインの停止（Ctrl+C）では、それまでに書いた内容を残す（利用者の決定）。

| 書き方 | 使う場合 | 元に戻す方法 |
|---|---|---|
| メモリに写してから直接書く（第五次の仕上げ） | 書く内容（符号化した後のバイト列）と元のファイルが、どちらも境目 T（**1 MiB** = 1,048,576 バイト）以内の上書き。ハードリンク・シンボリックリンクの先の実体・フォルダーにファイルを作る権限が無い場合も含む。まだ無いファイルで書く内容が T 以内なら、直接作って書く | 元のファイルの中身を書く直前にメモリに読んでおき、そこから書き戻して元の長さに戻す（まだ無かったファイルは消す） |
| 置き換え | T を超える上書き・新規作成。シンボリックリンク・ジャンクションは最後までたどり、実体のフォルダーに一時ファイルを作って実体を置き換える（リンクは残す） | 一時ファイルを消す |
| 写してから直接書く | T を超えるハードリンク（Windows でリンク数が 2 以上）と、フォルダーにファイルを作る権限が無い場合（一時ファイルを作るときに権限で失敗した場合） | 一時フォルダー（`Path.GetTempPath()`）の写しから書き戻す |
| 追記 | `Add-ProbedContent`・`-Append` | 追記を始める前の長さに切り詰める（追記先が無ければ、作ったファイルを消す） |

**メモリに写してから直接書く方法の規則（第五次の仕上げ。実装記録 10.16 節）。** 第五次の前半から、1000 個の小さなファイルへの上書きが第四次の約 10 倍遅くなっていた（`File.Replace` の費用。実装記録 10.15 節）ため、小さなファイルの書き方を変えた。

1. 書く内容を T までメモリにためる。表現できない文字の検査は今までどおり、ためる前に行う
2. 書き終えた時点で T 以内なら: 書き込み先が既にあり、その大きさも T 以内のときは、元のファイルを切り詰めずに開き、中身をメモリに読み、書いて長さを合わせる。
   失敗したら、メモリの写しから書き戻して元の長さに戻す。書き込み先がまだ無ければ、開いた時点で直接作っておき（完了するまでは空のファイルとして見える）、そこへ書く。失敗したら消す
3. 書く内容が途中で T を超えたら、その時点で上の表の置き換え・写してから直接書く方法に切り替え、ためていた分から書き始める（まだ無いファイルは、作った空のファイルを消してから一時ファイルに書く）
4. 開いた時点で元のファイルが T を超えていれば、初めから置き換え・写してから直接書く方法を使う（完了するまでに T を超えた場合も、その時点で切り替える）
5. メモリにためる量は、プロセス全体で 64 MiB まで（`Set-ProbedContent` は、パイプラインの終わりまで書き込み先をすべて開いておくため）。超えそうになったファイルは、その時点で 3 と同じく切り替える

- 既存のファイルを開くのは完了の時点で、それまでは元のファイルに触れない。ほかのハンドルが開いていて失敗するのは、置き換えと同じく完了の時点になる。
  ただし失敗する開き方は違う: **置き換えは、相手が削除の共有を許していないと、直接書く方法は、相手が書き込みの共有を許していないと失敗する**（実装記録 10.16 節の表）
- 書き戻しにも失敗した場合（ほかのプロセスがファイルの範囲をロックしたなど）は、メモリの写しを一時フォルダーの `SnowStack.EncodingProbe.<8 桁>.probedbak` に書き出して残し、
  写してから直接書く方法と同じく、エラーのメッセージ（`ErrorDetails`）にそのパスを示す（`RestoreFromBackupFailed`）
- **既知の限界: 書いている最中にプロセスが強制終了される（タスク マネージャーで終了する・電源が切れるなど）と、T 以内のファイルが書きかけ（または空）で残ることがある。**
  置き換えは、書き終えるまで元のファイルに触れないので、この限界が無い。Ctrl+C（パイプラインの停止）は強制終了ではなく、それまでに受け取った内容を書く
- **既知の限界: まだ無いファイルは、開いた時点で 0 バイトのファイルとして作るので、完了するまでほかのプロセスからは 0 バイトに見える。完了する前にプロセスが強制終了されると、0 バイトのファイルが残ることがある**（利用者が受け入れた）
- **ファイルの ACL に従う（利用者の決定）。** ファイルに WriteData の拒否があるなど、書き込み用に開く権限が無いファイルは、大きさによらず `WriteAccessDenied` で、元のファイルは変わらない（標準の `Set-Content` と同じ。1.2.0 仕様書 2.9 の「`-Force` はセキュリティ上の制限を越えない」と同じ考え方）。
  置き換え（`ReplaceFile`）はフォルダーの権限で行われるので、そのままでは T を超えるファイルだけ書けてしまう。そこで、置き換える前に元のファイルを書き込み用に（切り詰めずに、すべての共有を許して）開けるかを確かめ、すぐに閉じる。
  確かめるときの共有違反は失敗としない（ほかのハンドルが開いているときに失敗する条件を、置き換えの条件より厳しくしないため）。
  権限が無いと分かる時点は、大きさによらず開く時点（第六次 B で T 以内もそろえた。26.7。それまでは T 以内は完了の時点だった）

- リンク切れのシンボリックリンク: `Set-ProbedContent` は書かずに非終了エラー `LinkTargetNotFound`（標準の `Set-Content` も書かない。両ホストで実測）。
  `Out-ProbedFile`・`Export-ProbedCsv`・`Convert-ProbedContent -Destination`・追記は、リンクの先にファイルを作る（標準の `Out-File`・`Export-Csv`・`Add-Content` と同じ）。
  **Linux では、追記（`Add-ProbedContent`・`-Append`）はエラーになる**（既知の制限 D3。28 章）
- 読み取り専用の検査と `-Force` は、リンクの先の実体に対して行う
- Linux / macOS: 置き換える前に、元のファイルのアクセス権（UnixFileMode）を一時ファイルに写す。所有者は写せない。ハードリンクは切れる（既知の限界。T を超える場合。T 以内はメモリに写してから直接書くので切れない。28 章の D1）
- 属性（読み取り専用・隠し）・作成日時・代替データストリーム・ACL は、4 つの書き方のどれでも、ハードリンク・シンボリックリンク経由でも、書き戻した場合も保たれる（Windows で両ホストを実測。実装記録 10.6 節・10.16 節）
- ほかのプロセスが書き込み先を開いていると、置き換えとメモリに写してから直接書く方法が失敗するのは、開く時点ではなく完了の時点になる（受け入れた限界。ヘルプに書いた）
- 写してから直接書く方法は、大きなファイルでは写す時間がかかる（ヘルプに書いた）

**同じファイルの判定。** 読み取り中のファイルへの書き込み（`SamePathRoundTrip`）と、その逆向き（書き込み中のファイルを読み込み側が後から開く。第六次 B。26.4）、書き込み先の重複、`Convert-ProbedContent` の N8・N9 は、ファイルの実体で比べる（`Internal/FileIdentity`）。

- Windows: ファイルを開いて `GetFileInformationByHandle` で、ボリュームのシリアル番号とファイル ID を比べる（ReFS の 128 ビットのファイル ID は扱わない。既知の限界）。
  `\\?\`・UNC の管理共有・`\\.\`・subst・シンボリックリンク・ジャンクション・ハードリンクを同じ実体と判定する。まだ無いファイルは、親フォルダーの実体と名前で比べる
- Linux / macOS: リンクを解決したフルパスで比べる。ハードリンクは別のファイルとみなす（既知の限界。追記では終わらずに増え続ける。28 章の D2）
- 比べる時点: 上書きは書き始める前（一時ファイル・新しいファイルを作る前。メモリに写してから直接書く方法でも同じ時点）、追記は「切り詰めずに開く → 開いたハンドルで比べる → 書く」
- `a.txt::$DATA` は `a.txt` として扱う。代替データストリーム（`a.txt:alt`）は両ホストで `AlternateDataStreamNotSupported`

## 17. CSV の書き出し

移植した `ExportCsvHelper` のとおりに書き出す。主な規則（すべて 7.x の `Export-Csv` と同じ。実測報告 M4 の 7.6.7 の結果と一致すること）:

| 項目 | 規則 |
|---|---|
| 列 | 最初のオブジェクトのプロパティ（拡張・アダプテッド）で決め、順序を固定する。2 件目以降で足りない列は空、余分なプロパティは書かない（24 章 U1） |
| 辞書（`IDictionary`） | キーを列とし、ETS で追加された拡張メンバーも列に加える（5.1 の標準は辞書オブジェクト自体のプロパティ `Count` / `Keys`… を書く） |
| 値の文字列化 | プロパティの値の `ToString()`。`$null` と取得時の例外は値なし（区切り文字だけ）。日付・数値は現在のカルチャーの書式になる |
| 引用符（`Always`） | すべての値を `"` で囲み、値の中の `"` は `""` にする。値が無い（`$null`）列は何も書かない |
| 引用符（`AsNeeded`） | 区切り文字、LF、`"` のいずれかを含む値だけ囲む（**CR だけを含む値は囲まない。移植元のとおり**） |
| 引用符（`Never`） | 囲まない（値に区切り文字があると CSV が壊れる。標準と同じ） |
| `-QuoteFields` | 指定した列（大文字小文字を区別しない）だけ囲む |
| ヘッダー行 | 列名を、値と同じ引用符の規則で書く |
| `#TYPE` 行 | `-IncludeTypeInformation` を指定したときだけ、ヘッダーの前に書く。型名が `CSV:` で始まる場合は除く |
| 区切り文字 | `-Delimiter`、`-UseCulture`（`CurrentCulture.TextInfo.ListSeparator` の 1 文字目）、既定は `,` |

**`-UseCulture` の区切り文字は、ホストの .NET のカルチャーのデータに従う（第六次 C。BUG-0029。挙動は変えない）。** 標準の `Export-Csv` / `Import-Csv` と同じく、`ListSeparator` はホストの .NET（5.1 は NLS、7.x は ICU）から取るので、
ms-ID・fa-AF・es-BZ・ga-GB・it-VA・ps-PK・ff-Latn-* など 36 のカルチャーでは、5.1 が `;`、7.x が `,` になる（ja-JP・en-US・de-DE・fr-FR・ko-KR・zh-* などの主なカルチャーは同じ）。
一方のホストで `-UseCulture` で書いた CSV を、もう一方のホストの `-UseCulture` で読むと、列が分かれない。ホストをまたぐ場合は `-Delimiter` で区切り文字を明示する。
日付・数値の書式がホストで違うこと（BUG-0005）と同じ扱いで、`Import-ProbedCsv -UseCulture`（11 章）も同じ。`Import-ProbedCsv` / `Export-ProbedCsv` のヘルプの `-UseCulture` に書いた

**数値の既定の表記も、カルチャーによらずホストの .NET で違うことがある（第六次 C で明記。既知の限界）。** 値の `ToString()` で文字列にするため、
`0.1 + 0.2` は 5.1 が `0.3`（.NET Framework は 15 桁で丸める）、7.x が `0.30000000000000004`（.NET Core 3.0 以降は往復できる最短の表記）、`-0.0` は 5.1 が `0`、7.x が `-0` になる。
両ホストで同じにするには、書式を指定して文字列にしたプロパティを渡す（`$x.ToString('G15', [cultureinfo]::InvariantCulture)` など）。`Set-` / `Add-ProbedContent` の文字列化は 1.1.0 仕様書 5.8

## 18. `-Append`

### 18.1 共通の規則

1.2.0 仕様書 2.8 と同じ。

- 追記先の既存ファイル（1 バイト以上）には BOM を書かない
- 追記先が無い、または 0 バイトなら、新規作成と同じ扱い（ヘッダーを書く。`-NoHeader` なら書かない）
- 整合性検査（バイト列比較）を行う。`-AllowEncodingChange` で行わない
- ISO-2022 の追記先が ASCII 以外の状態のまま終わっていれば、追記の前に ASCII に戻す（18.4。第六次）

### 18.2 列の照合

追記先（1 バイト以上）のヘッダーを、移植した `ReadHeader` で読む（判定した文字エンコーディングで、BOM の後ろから復号する）。

- 追記先のヘッダーの列の**順序と表記**で書く（列名の照合は大文字小文字を区別しない。実測報告 M5 i）。
  比べ方は 5.1 でも .NET 10 の `OrdinalIgnoreCase` と同じで、照合した列の値もその規則で引く（25.3。第六次）
- ヘッダーを読むとき、取り除く BOM はファイル先頭の 1 個だけ（2 個目の U+FEFF は最初の列名に残る。25.1。第六次）
- 追記するオブジェクトに、追記先の列に当たるプロパティが無い場合は終了エラー（ID `CannotAppendCsvWithMismatchedPropertyNames`）。
  `-Force` を指定した場合は、その列を空にして書く
- 追記するオブジェクトの、追記先の列に無いプロパティは書かない（標準と同じ。24 章 U1）
- ヘッダー行と `#TYPE` 行は書かない
- `-NoHeader` は受け付ける（PowerShell 7.6.7 と同じ。master のソースは拒否するが、リリース版に合わせる）。列の照合は `-NoHeader` が無い場合と同じに行う
- 追記先が 1 バイト以上で、ヘッダーが読めない（空行と `#` の行だけなど）場合は、移植元の挙動に合わせる。挙動を実測報告と同じ形で確かめ、実装記録に残す
- **追記先のヘッダーに空の列名がある場合（第五次。実装記録 9 章の実測）。** 標準（7.6.7 と 5.1）は、`-Force` なしは `CannotAppendCsvWithMismatchedPropertyNames`、
  `-Force` ありは空の名前でプロパティを引こうとして `PSArgumentException`（ID は汎用の `Argument`、文言は .NET の「"name" の値が無効」）で止まる。
  止まる点は標準に合わせ、`-Force` ありは ID `CannotAppendCsvWithEmptyPropertyName`（InvalidData）と本モジュールのメッセージにする。
  末尾の空の列名（`A,B,`）は、標準と同じく無視して追記する

### 18.3 追記先の最後の行に改行が無い場合

**標準の `Export-Csv` は、追記先の最後の行に改行が無いと、新しい行をつなげてしまう**（実測報告 M5 j: `1,2"x","y"`。両ホストで同じ）。CSV が壊れる。
`Export-ProbedCsv` は、これを直す。

- 追記先の末尾が改行（判定した改行の型での LF または CR）で終わっていない場合は、**最初のレコードを書く前に、16.3 で決めた改行を 1 個書く**
- 末尾の判定は、2.3 の改行の型（追記先の文字エンコーディングから決まる単位）で行う。UTF-16 / UTF-32 では、最後の 2 / 4 バイトを見る
- この改行も整合性検査の対象とする（改行は ASCII なので、通常は検査を通る）
- 入力が 0 件の場合は、追記先に触れない（改行も書かない。1.2.0 仕様書 2.11）
- 追記先が 0 バイトの場合は、新規作成と同じ扱いなので、改行を書かない
- 追記先が ISO-2022 で ASCII 以外の状態のまま終わっている場合は、この改行の前に ASCII に戻すシーケンスを書く（18.4）
- **既知の限界（第六次 C。BUG-0023。1.4.0 で検討する）:** 追記先の最後の値の引用符が閉じていない場合（`1,"2` で終わる、途中で切れたファイルや手で編集したファイル）は、
  補った改行と追記したレコードが、その引用符の中に入る。読み戻すと、追記したレコードは前の値の続き（`2` CRLF `x"` など）になり、レコードの数が増えない。
  警告もエラーも出さない（標準の `Export-Csv -Append` も同じ結果になる。標準は改行も補わない）。末尾が引用符の中かどうかを見て止める・警告するかは 1.4.0 で検討する。
  `-Append` のヘルプに書いた

### 18.4 ASCII 以外の状態のまま終わる ISO-2022 の追記先（第六次。BUG-0018）

ISO-2022 は状態を持つ文字エンコーディングで、RFC 1468 は「行は ASCII の状態で終わる」と定める。途中で切れたファイルや断片をつないだファイルは、
JIS X 0208 の状態（`ESC $ B` の後ろ）のまま終わることがある。そこへ ASCII のバイトをそのまま足すと、追記した行・レコードが 2 バイト文字として読まれて失われる。
改行は状態を戻さない（.NET の復号も同じ）ので、JIS のまま CRLF で終わっている形も同じである。

`Add-ProbedContent`・`Out-ProbedFile -Append`・`Export-ProbedCsv -Append` は、**書く文字エンコーディングが ISO-2022-JP（50220・50221・50222）・ISO-2022-KR（50225）の場合**
（追記先から継承した場合と、`-Encoding` で明示した場合）、追記先の末尾の状態を調べ、追記の前に次を書く。

| 追記先の末尾の状態 | 書くもの |
|---|---|
| ISO-2022-JP で、SO（`0E`）の後に SI（`0F`）が無い | SI |
| ISO-2022-JP で、最後の G0 の指示（`ESC ( F`・`ESC $ F`・`ESC $ ( F`）が `ESC ( B` 以外（`ESC ( J`・`ESC ( I` も含む） | `ESC ( B` |
| ISO-2022-KR で、SO の後に SI が無い | SI（G0 は常に ASCII） |

- 両方に当たれば SI、`ESC ( B` の順に書く。G1 の指示（`ESC ) F`・`ESC $ ) F`）とそれ以外の ESC、末尾で途中で切れたエスケープシーケンスは状態に数えない
- 書く順序は「戻すシーケンス → 18.3 で補う改行 → 追記する内容」
- 1 バイト以上書くときにだけ書く。入力が 0 件の場合・`-WhatIf` の場合は、追記先に触れない
- 戻すシーケンスも、エラーで止まったら残さない（「エラーで止まったら、そのファイルには、その呼び出しで書いた分を残さない」。16.4・16.5）
- **`-AllowEncodingChange` で別の文字エンコーディング（UTF-8 など）を追記する場合は、追記先の状態に手を入れない**（利用者の決定）。文字エンコーディングの混在を利用者が認めた場合であり、
  追記先を ISO-2022 として読み戻すことを前提にしないため
- 末尾の状態は、末尾から逆向きに読んで求める。ISO-2022 では `1B`・`0E`・`0F` は制御の意味でしか現れないので、最後の G0 の指示と最後の SO / SI が見つかった時点で止める。
  SO / SI を使わないファイルは、無いことを確かめるために先頭まで読む（継承する場合は、その前の判定でファイル全体を読んでいるので、同じ程度の費用）
- HZ（52936）は対象にしない。HZ のファイルは判定では `us-ascii`（継承すると UTF-8）になり、追記先として継承されない。
  `-Encoding hz-gb-2312` を明示して `~{` のまま終わる追記先に追記すると、`~}` を書かずに足すので、HZ として読むと追記した内容が化ける（既知の限界。実装記録 11 章）

## 19. ファイルを開く時点・空の入力・その他

すべて `Out-ProbedFile` と同じ（1.2.0 仕様書の該当節）。

| 項目 | 規則 | 1.2.0 仕様書 |
|---|---|---|
| ファイルを開く時点 | 最初の行を書く直前。`Import-ProbedCsv a.csv \| Export-ProbedCsv a.csv` は `SamePathRoundTrip` で止まり、元のファイルは壊れない。書き込み側が先に開いたファイルを読み込み側が後から開く逆向きの往復（`Import-ProbedCsv a.csv, z.csv \| Export-ProbedCsv z.csv`）も、書き込みを元に戻して `SamePathRoundTrip` にする（第六次 B。BUG-0028。26.4） | 2.10 |
| `BeginProcessing` の検査の順序 | パラメータ → パス → `-NoClobber` → 読み取り専用 → `-EncodingFrom` の判定（と検証）→ 出力先・追記先の判定（と検証）・追記先のヘッダーの読み取り → `ShouldProcess` | 2.10 |
| 空の入力 | `-Append` なし: 0 バイトで作成（既存は 0 バイトに切り詰める）。`-Append` あり: 既存に触れない、無ければ 0 バイトで作成（標準の `Export-Csv` と同じ。実測報告 M6） | 2.11 |
| BOM | 1 行でも書いたときにだけ書く | 2.11 |
| パスの解決 | ちょうど 1 件に解決されること | 2.12 |
| `-NoClobber` / `-Force` / 読み取り専用 | 同じ組み合わせの表。読み取り専用は、書き込み後に属性を戻す | 2.9 |

### 25.1 BOM が 2 個以上続くファイル（BUG-0021）

読み込みのすべての経路（`Get-ProbedContent`・`-Raw`、`Import-ProbedCsv`、`Export-ProbedCsv -Append` の追記先のヘッダー、`-DetectionLineCount` の検証の後の読み込み）で、
**取り除く BOM はファイル先頭の 1 個だけ**とする。2 個目の U+FEFF は文字として残す（7.x の標準の `Get-Content`・`Import-Csv` と同じ）。
`-Encoding` の指定（`Auto`・`utf8BOM` などの BOM 付きの語彙・`NoBOM`・裸名・WebName・数値・`Encoding` のインスタンス）によらない。

- 1.1.0 から、BOM 付きの語彙を指定した場合と、判定した「BOM あり」の結果で読む場合（追記先のヘッダー）に、2 個目まで取り除いていた
  （`StreamReader` は `detectEncodingFromByteOrderMarks: false` でも、渡された Encoding の preamble と一致する先頭を読み飛ばす）
- `Get-ProbedContent -Raw` で読んで `Set-ProbedContent -EncodingFrom <同じファイル> -NoNewline` で書き戻すと、元のバイト列と一致する
- BOM が 2 個続く CSV に `Export-ProbedCsv -Append` すると、最初の列名を U+FEFF 付きで読むので、7.x の標準の `Export-Csv -Append` と同じく `CannotAppendCsvWithMismatchedPropertyNames` になる
- `Convert-ProbedContent` は、もともと 2 個目を文字として保っていた（変えていない）

### 25.2 途中で切れたファイルの末尾（BUG-0042）

読み込みのコマンド（`Get-ProbedContent`・`-Raw`、`Import-ProbedCsv`、`Export-ProbedCsv -Append` の追記先の読み取り）は、ファイルの末尾で途中で切れた文字を、
**5.1 でも 7.x と同じく、置換フォールバックの文字として読む**。7.x（.NET）の `StreamReader` はストリームの終わりで Decoder を flush し、5.1（.NET Framework）は flush しないで黙って捨てていた。

- すべての文字エンコーディングに当てはめる（利用者の決定）。長さが奇数の UTF-16 の末尾の 1 バイト・対になっていない上位サロゲート、UTF-32 の 1〜3 バイト、
  途中で切れた UTF-8、2 バイトのコードページ（932・949・950・936 など）・EUC の先行バイト、ISO-2022 の途中で切れたエスケープシーケンスと 2 バイト文字など
- 置き換えの文字は文字エンコーディングの復号器による（UTF 系は U+FFFD、932・EUC-JP・ISO-2022-JP は `・`（U+30FB）、949・950・936 などは `?`、
  途中で切れた ESC は ESC と後続の文字そのもの）。両ホストで同じ
- **既知の差:** GB18030（54936）の途中で切れた 4 バイトの列（`81 30`・`81 30 81`）は、.NET Framework と .NET の復号器の違いで、置き換えの文字の数が違う
  （7.x は `? 0` / `? 0 ?`、5.1 は `?` / `? ?`）。直さない（実装記録 11 章）
- `Convert-ProbedContent` は今のまま。途中で切れた文字は不正なバイト列として変換しない（`InvalidSourceBytes`。1.2.0 仕様書 13.2）

### 25.3 CSV の列名の比較（BUG-0020）

列名を比べる箇所は、**5.1 でも 7.x（.NET 10）の `StringComparison.OrdinalIgnoreCase` と同じ結果にする。** 7.x は実行環境の比較をそのまま使い、
5.1 では .NET 10 の同値類から作った表（`Internal/CsvNameCaseTable.cs`。`tools/New-CsvNameCaseTable.ps1` が生成）で比べる。

| 箇所 | コマンド |

|---|---|
| `-Value @('a', $null, 'b')` | `61 0D 0A 62 0D 0A` |
| `-Value @('a', $null, 'b') -NoNewline` | `61 62` |
| `-Value @($null, $null)` | 空のファイル（既存なら空にする。`-Value $null` と同じ） |
| `-Value @($null, $null)` の `Add-` | 何も足さない（追記先が無ければ空のファイルを作る） |

パイプラインで渡した場合は、もともと標準と同じだった。

### 25.5 `ansi` / `oem`（BUG-0032）

`ansi` / `oem` の語彙（すべての `-Encoding` と `ConvertTo-DotNetEncoding`）と、`Get-EncodingProbePlatformInfo` の `Locale` の `AnsiCodePage` / `OemCodePage` は、次の値にする（1.1.0 仕様書 3.3 の「実行環境の ANSI コードページ」をこう定める）。

- **Windows: システムのロケール（「Unicode 対応ではないプログラムの言語」）の ANSI / OEM コードページ**（`GetACP` / `GetOEMCP`。net48 と net10.0 の両方）。
  スレッドのカルチャー（`CurrentCulture`。「地域」の形式）には従わない。5.1 の `Default` / `Oem`、7.x の `oem`、
  5.1 の 0 バイトのファイルの既定（ANSI）と同じ値になる。第五次までは `CurrentCulture.TextInfo` の値だった。
  **標準の 7.x の `-Encoding ansi` は、プロセスの開始時の現在のカルチャー（「形式」）の ANSI コードページなので、「形式」をシステムのロケールと違う値にしている環境では本モジュールと違う**
  （例: 日本語の Windows で形式を英語（米国）にすると、標準は 1252、本モジュールは 932）。
  第六次 A ではここに「標準の 7.x の `-Encoding ansi` と同じ」と書いていた。測り方の誤りで、リリース前の補足で訂正した（実装記録 15.6 節）
- **システムの ANSI / OEM が 65001**（「ベータ: ワールドワイド言語サポートで Unicode UTF-8 を使用」）**の場合は、BOM 無しの UTF-8 として扱う**（`Encoding.GetEncoding(65001)` は BOM 付きのインスタンスを返すため、組み立て直す）。
  この設定の環境は手元で作れなかった（OS の設定の変更と再起動が要る）ので、標準のコマンドとは比べていない（実装記録 11 章）

  Linux（Ubuntu 24.04、.NET 10.0.14、PowerShell 7.6.9）で実測した値は次のとおり。現在のカルチャーは環境変数 `LC_ALL`・`LANG` などから決まる（`LC_ALL` が優先。空の文字列を設定した `LC_ALL` も優先され、不変カルチャーになる）

  |---|---|---|---|
  | 未設定・`C`・`POSIX`・`C.UTF-8` | 不変カルチャー | 1252 | 437 |
  | `en_US.UTF-8` | en-US | 1252 | 437 |

  | `ru_RU.UTF-8` | ru-RU | 1251 | 866 |
  | `ko_KR.UTF-8` | ko-KR | 949 | 949 |

  | `ar_SA.UTF-8` | ar-SA | 1256 | 720 |

  同じ環境の標準の 7.6.9 の `-Encoding ansi` は、モジュールの `ansi` と同じコードページだった。**標準の `-Encoding oem` は UTF-8 で、モジュールの `oem` と違う。**
  macOS は**実測していない**。.NET のソースからの推定では、Linux と同じく現在のカルチャーの `TextInfo` の値になる（現在のカルチャーの決まり方は確かめていない）
- **`-Encoding 0`（数値・文字列）は拒否する。** 0 は語彙に無く、`Encoding.GetEncoding(0)` は実行環境の既定（.NET Framework は ANSI、.NET は UTF-8）を返すため。

### 25.6 UTF-7 の `Encoding` のインスタンス（BUG-0037）

書き込みのすべてのコマンドで、コードページが 65000 の `System.Text.Encoding` のインスタンス（`UTF7Encoding` など）を、名前の `utf7` と同じエラーで拒否する
（`Convert-ProbedContent` は `EncodingNotAllowedForWrite`、ほかの 4 コマンドは束縛の段階の `ParameterArgumentTransformationError`）。
第五次までは `Convert-ProbedContent` だけがインスタンスを受け付けて UTF-7 で書いていた。

### 25.7 曖昧な組み合わせの解消（BUG-0031。クラスライブラリ）

バイト列だけでは区別できない組み合わせ（EUC-JP と Shift_JIS、EUC-KR と CP949、EUC-TW と CP950）をカルチャーと改行で決める処理で、
**判定に使った標本を、決めた候補では厳密に（例外フォールバックで）復号できず、もう一方では復号できる場合は、もう一方を選ぶ。**

- どちらの候補も厳密に復号できない場合は、今までどおりカルチャーと改行で決める
- その TFM で作れない候補（EUC-TW の 51950。net48・net10.0 とも作れない）は外さない（「復号できない」とみなさない）。両 TFM で同じ結果になる
- 復号を確かめるのは判定に使った標本だけ（`-DetectionLineCount` では切り出した先頭の行）
- 短い EUC-JP の日本語（約 40 バイト以下）を、ja-JP の CRLF・改行なしで Shift_JIS と判定し、黙って化けて読んでいた。CP932 に割り当ての無い 2 バイト（`FC CB` など）を含むため、厳密に復号できない

## 26. 第六次 B で改めた挙動（BUG-0025・0026・0027・0028・0030・0035、ACL の時点）

テスト担当のブラックボックステストへの対応（2026-10-26）。変えた挙動は CHANGELOG の「挙動の変更（PowerShell モジュール。第六次 B）」、実測と決定の根拠は実装記録 12 章。

### 26.1 隠し・システム属性のファイル、代替データストリーム、Archive 属性、WriteAccessDenied のメッセージ（BUG-0025）

- 書き込みの 4 コマンドと `Convert-ProbedContent` は、`-Force` なしで隠し・システム属性のファイルに書き、代替データストリームを保つ（第五次で直っていたことを確かめた。1 MiB 以内・超えるのどちらも）。
  **標準の `Out-File` / `Export-Csv` は、両ホストとも隠し・システム属性のファイルに書けず（`FileOpenFailure`。`-Force` でも同じ）、代替データストリームを消す。** `Out-ProbedFile` / `Export-ProbedCsv` はこれと違う（利用者が受け入れた）。
  標準の `Set-Content` とは同じ
- **書き込みに成功したら、4 つの書き方（メモリに写してから直接・置き換え・写してから直接・追記）のどれでも Archive 属性を付ける**（Windows のふつうの挙動。標準の `Set-Content` も付ける）。
  置き換え（`ReplaceFile`）は元のファイルの属性を写すので、1 MiB を超える上書きで消えていた。**元に戻した場合は、書き込みの前の属性のまま**（書き戻しでファイルシステムが付ける Archive も外す）。
  追記で何も書かなかった場合は、属性を変えない
- `WriteAccessDenied` のメッセージは、本モジュールの 5 言語のメッセージ（`WriteAccessDenied`）。.NET の例外の文面（7.x では英語）を出していた。内部例外は持たない（実行環境依存の文言を見せない）

### 26.2 ほかのプログラムが開いているファイル（BUG-0026）

判定と変換の読み取りは、`Get-ProbedContent` と同じ共有モード（`FileShare.ReadWrite`）で開く。

| 箇所 | 第五次まで | 第六次 B |
|---|---|---|
| `Get-ProbedContent`・`Import-ProbedCsv`・`-DetectionLineCount` の切り出しと検証・`Export-ProbedCsv -Append` のヘッダーと末尾の読み取り・ISO-2022 の末尾の状態 | ReadWrite | 変えない |
| `Resolve-Encoding`（クラスライブラリの `Detect(path)`） | Read | ReadWrite（モジュールで読んで `Detect(bytes)` に渡す。テストデータ 1200 件で結果が同じことを確かめた） |
| 書き込み先・追記先・`-EncodingFrom` の参照ファイルの判定（`EncodingInheritance.FromFile`） | Read | ReadWrite |
| `Convert-ProbedContent` の変換元 | Read | ReadWrite |
| 書き込み（追記の FileStream・直接書く・写しを作る `File.Copy`） | Read | 変えない（ほかのハンドルが開いているときに失敗する条件を変えない） |

- それでも開けない場合（相手が読み込みの共有を許していない）は、`ReadFailed`（ReadError）・`ReadAccessDenied`（PermissionDenied）の 5 言語のメッセージ。
  共有違反・ロック違反は「ほかのプログラムが使用中」、それ以外はエラー コード（HRESULT）を示す
- `Resolve-Encoding` は、読めないファイルを非終了エラーにして次のファイルへ進む（第五次までは生の `IOException` の終了エラーで、残りのファイルを処理しなかった）
- 追記（`Add-ProbedContent`・`-Append`）は、ほかのプログラムが書き込み用に開いている間は今までどおり書けない（`WriteFailed`。5 言語のメッセージ）。
  追記の開き方が書き込みの共有を許さないためで、変えていない（交互に書いて壊さないため）。7.x の標準の `Add-Content` は書き、5.1 の標準は `GetContentWriterIOError`
- 書き込みの `WriteFailed` のうち、共有違反・ロック違反だけを 5 言語のメッセージにする（ディスクの空き不足などは .NET の文面のまま）。
  **第六次 C で、それ以外もエラー コード（HRESULT）を示す 5 言語のメッセージにした（27.5）**
- クラスライブラリの `EncodingDetector(string path)` の共有モード（Read）は変えない（利用者の決定。モジュールは使わない）

### 26.3 一時ファイルの名前（BUG-0027）

- 置き換えに使う一時ファイルの名前を、元の名前によらない固定長の `.~probed<8 桁の 16 進>.probedtmp`（26 文字）にした。名前がぶつかったら作り直す。
  `.<元の名前>.<8 桁>.probedtmp` だったので、名前の長いファイル（7.x では 1 つの名前の上限 255 文字、5.1 ではパスの上限 260 文字に当たる）への 1 MiB を超える書き込みと変換が `WriteFailed` になっていた
- それでも一時ファイルのパスが長さの上限を超える場合（5.1 で、名前の短いファイルが深いフォルダーにあるなど）は、写してから直接書く方法（まだ無いファイルは直接作る）に切り替える
- **既知の限界:** 一時ファイルの名前から書き込み先が分からない。書いている最中にプロセスが強制終了されて一時ファイルが残っても、どのファイルのものかは名前からは分からない（書き込み先と同じフォルダーにある）
- 1 MiB 以内の上書きは一時ファイルを使わない（16.5）。`TemporaryFileRegistry`（ワイルドカードの解決から一時ファイルを除く）はパスで登録しているので、影響しない

### 26.4 逆向きの往復（BUG-0028。案 A）

書き込み側が先に開いたファイルを、同じパイプラインの読み込み側が後から開いた場合も `SamePathRoundTrip` にする。

- **両方がエラーを出す。** 読み込み側は、読む前にファイルの実体（16.5 の同じファイルの判定）で書き込み中の表と比べ、当たれば読まずに、書き込み側を元に戻させてから非終了エラー `SamePathRoundTrip` を出して次へ進む。
  書き込み側は、そのファイルへの以後の入力を書かず、次の入力か完了の時点で `SamePathRoundTrip` を出す（`Set-` / `Add-ProbedContent` は非終了、`Out-ProbedFile` / `Export-ProbedCsv` は終了エラー）
- 書き込みは「エラーで止まったら、そのファイルには、その呼び出しで書いた分を残さない」の規則で元に戻す

  | 書き方 | 1 MiB 以内 | 1 MiB を超える |
  |---|---|---|
  | 既存のファイルの上書き | メモリに写してから直接書く: まだ書いていないので、ためた分を捨てる | 置き換え: 一時ファイルを消す。写してから直接書く: 写しから書き戻す |
  | まだ無いファイル | 開いた時点で作った空のファイルを消す | 一時ファイルを消す（書き込み先はまだ無い） |
  | 追記 | 元の長さに切り詰める（追記先が無ければ、作ったファイルを消す） | 同じ |

- まだ無いファイルは、親フォルダーの実体と名前で比べる。**読み込み側でファイルが見つからなかった場合もこれで引き、当たれば「ファイルが無い」（FileNotFound）ではなく `SamePathRoundTrip` にする**（利用者の決定。1 MiB を超える新しいファイルでエラーの種類が変わらないようにするため）
- 比べる箇所と比べない箇所

  | 箇所 | 比べるか | 理由 |
  |---|---|---|
  | `Get-ProbedContent`（行・`-Raw`） | 比べる | 読んだ内容が同じパイプラインの書き込みに流れる |
  | `Import-ProbedCsv`（`-DetectionLineCount` を含む） | 比べる | 同上。切り出し・検証より前に比べる |
  | `Convert-ProbedContent` の変換元 | 比べる | 書き込み中のファイルを読んで書き換えると、書き込み側の完了と衝突する |
  | `-EncodingFrom` の参照ファイル | 比べない | `BeginProcessing` で読むので、同じパイプラインの書き込み側はまだ開いていない |
  | 書き込み側が自分の書き込み先を判定・読み取る（追記先の判定、`Export-ProbedCsv -Append` のヘッダーと末尾、ISO-2022 の末尾の状態） | 比べない | 自分が開く前（登録する前）に読む。ほかの書き込みのコマンドとの衝突（書き込み同士）は、読み込みと書き込みの往復の範囲の外 |
  | `Resolve-Encoding` | 比べない | 内容を流さない（判定の結果だけを出す）。書き込み側のファイルを変えない |

- 1 MiB 以内の上書きと 1 MiB を超える置き換えでは、第五次までは元のファイルに触れていないので、読み込み側は元の内容を読み、エラーにならなかった（書いたファイルは「a の内容 + z の元の内容」）。第六次 B から、これもエラーになる（挙動の変更）
- 標準のコマンドは往復を検出しない（両ホストで実測。実装記録 12 章）。`Get-Content a,z | Out-File z` は止まらずに増え続け、`Set-Content` は z の元の内容だけを残す

### 26.5 大きなファイルとメモリ不足（BUG-0030）

- `Resolve-Encoding` は、全体を読む前に大きさを調べ、上限（2 GB）を超えれば `-DetectionLineCount` を案内するメッセージの非終了エラー（`EncodingDetectionFailed`）にする（5.1 では生の `OutOfMemoryException` / `IOException` だった）
- 全体を読む判定（`Resolve-Encoding`・`Get-ProbedContent`・`Import-ProbedCsv`・書き込み先と追記先・`-EncodingFrom`・`-DetectionLineCount` の切り出し）のメモリ不足は `NotEnoughMemoryToDetect`（InvalidData。各コマンドの判定の失敗と同じ扱い）
- `Convert-ProbedContent` は、上限を超えるファイルを読む前に `FileTooLargeToConvert`、メモリ不足を `NotEnoughMemoryToConvert`（どちらも LimitsExceeded の非終了エラー）にする。ファイルは変わらない
- **`Resolve-Encoding` のエラーの種類が混ざる（利用者の決定）。** ファイルが無い場合と、`-DetectionLineCount` で切り出す範囲が上限を超える場合は、今までどおり終了エラー。
  第六次 B で足したもの（読めない・全体の判定の上限を超える・メモリ不足）は非終了エラー。ヘルプに書いた
- 全体の判定がファイルの大きさの約 3.6 倍のメモリを使う点は、1.4.0 で扱う
- **対象外（既知の制限。リリース前の補足で書いた。実装記録 14 章）: 判定の後に 1 つの巨大な文字列を作る段階のメモリ不足は、生の `OutOfMemoryException` の終了エラーのまま。** 1.4.0 で ID の付いたエラーにすることを検討する。
  終了エラーなので、`-Path` に複数のファイルを渡した場合、残りのファイルは処理されない。該当する経路は次のとおり
  - `Get-ProbedContent -Raw`（ファイル全体を `StreamReader.ReadToEnd` で 1 つの文字列にする）
  - `Get-ProbedContent`（行で読む）で、改行の無い巨大な 1 行
  - `Import-ProbedCsv` の巨大なフィールド（改行の無いファイル、引用符で囲んだ複数行の値など）・巨大なヘッダー行
  - `Export-ProbedCsv -Append` で、改行の無い巨大な追記先（ヘッダーを読む段階）
  - `Convert-ProbedContent` は対象外ではない（ファイル全体の文字列を作る段階のメモリ不足も `NotEnoughMemoryToConvert`）
- 起きる条件は 2 つある。**`-Encoding` を明示しても避けられない**（判定を飛ばしても、文字列を作る段階のメモリの量は変わらない）
  - **Windows PowerShell 5.1 の 32 ビット版で、数百 MB のファイル**（テスト担当が 600 MB で確かめた）。`ReadToEnd` は文字数 n に対して、ためる途中で約 2n バイト、最後の文字列に連続した約 2n バイトを使う。避け方: 64 ビット版を使う、`-Raw` を使わずに行で読む
  - **復号した後の文字数が約 10.7 億を超えるファイル**（.NET の文字列の長さの上限。.NET 10 は 1,073,741,791 文字、.NET Framework もほぼ同じ）。文字数は UTF-16 の単位で数える（補助面の文字は 2）。
    英数字だけのファイルでは約 1 GiB、日本語が主の Shift_JIS / EUC では判定の上限（2 GB）の手前まで届かないことが多い。`-Encoding` を明示した場合は判定の上限が掛からないので、2 GB を超えるファイルでも同じく起きる。
    **64 ビット版でも、メモリが十分あっても避けられない。** 避け方: `-Raw` を使わずに行で読む、ファイルを分ける
- 標準の `Get-Content -Raw` も 1 つの文字列を作るため、同じ上限がある

### 26.6 内部で呼ぶ Out-String と利用者の既定値（BUG-0035）

- `Out-ProbedFile` が内部で呼ぶ `Microsoft.PowerShell.Utility\Out-String -Stream` に、利用者の `$PSDefaultParameterValues`（`'Out-String:Width'` など）が効かないようにする（新しいスコープで空のローカル変数にしてから、ステッパブルパイプラインを組み立てる）。
  標準の `Out-File` は `Out-String` を呼ばないので、影響を受けない
- `Out-ProbedFile -Width` への既定値（`'Out-ProbedFile:Width'`・`'*:Width'`）は、今までどおり効く（`'*:Width'` は `Out-File` にも効く）
- 内部で呼ぶホストのコマンドは `Out-String` だけ。利用者の状態で変わるが、意図どおりとして変えないもの: パスの解決（PSDrive・現在の場所）、`-Value` の文字列化（型データ）、
  `$FormatEnumerationLimit`・書式データ（`Out-File` も同じ影響を受ける）

### 26.7 ACL で拒否されたファイルの時点（前回の引き継ぎ）

ファイルの ACL で書き込みが拒否されている場合の `WriteAccessDenied` は、**大きさによらず開く時点**で出す（第五次の仕上げでは、1 MiB 以内は完了の時点だった）。
置き換える前と同じく、書き込み用に（切り詰めずに、すべての共有を許して）開けるかを確かめ、すぐに閉じる。共有違反は失敗としないので、ほかのハンドルが開いているときに失敗する条件（16.5）は変わらない。

## 27. 第六次 C で改めた挙動（BUG-0038・0039・0041・0045、WriteFailed のメッセージ）

テスト担当のブラックボックステスト（第 1 段階）の不具合のうち、パラメーター・メッセージの 5 件を直した。挙動を変えないで文書に書いたもの（BUG-0022・0023・0029・0034・0036・0040・0043・0044・0008 の追記）は、
各章・1.1.0 仕様書・1.2.0 仕様書・ヘルプ・README に書いた（実装記録 13 章に、BUG ごとの書いた場所の一覧がある）。

### 27.1 `-Culture` の前後の空白（BUG-0038）

`-Culture` も、`-Encoding`・`-Strategy` と同じく**名前の前後の空白（空白・タブ・改行）を除いてから**受け付ける（`' ko-KR'` は `'ko-KR'` と同じ）。
除いた名前を判定に渡すので、`Resolve-Encoding` の `Culture` にも除いた名前が出る。名前の途中の空白（`'ko KR'`）は今までどおり `InvalidCulture` で、メッセージと対象には渡された元の値を出す。
除くのはモジュールだけで、クラスライブラリの `EncodingDetectorOptions.Culture` の検証は変えない。空白だけの値は今までどおり省略と同じ。

前後の空白を除くパラメーター（第六次 C の後）:

| パラメーター | 除くところ |
|---|---|
| `-Encoding`（全コマンド）・`-SourceEncoding` | 統一語彙の解決（`EncodingVocabulary`。1.1.0 から） |
| `-Strategy` | `ResolveEncodingOptions.TryParseStrategy`（1.1.0 から） |
| `-Culture` | `ResolveEncodingOptions.TrimCulture`（第六次 C） |
| `-Bom`・`-LineBreak`・`-UseQuotes`（列挙型） | PowerShell の型変換（両ホストで除く） |

除かないもの: `-Path`・`-LiteralPath`・`-EncodingFrom`・`-Destination`（パス）、`-Header`・`-QuoteFields`（列名。標準と同じ）、`-Delimiter`（1 文字）。

### 27.2 逆シリアル化した判定結果（BUG-0039）

`Export-Clixml` と `Import-Clixml`・ジョブ（`Receive-Job`）・リモート・`Select-Object *`・`ConvertFrom-Json` を通した判定結果（`Deserialized.SnowStack.EncodingProbe.EncodingInformation` などの `PSCustomObject`）は、
**今までどおり受け付けない**（型が違い、どの値をどう扱うかを決められないため）。メッセージを「文字エンコーディング '' を解決できませんでした」から、
型名と、渡し方（`CodePage` の値、または BOM を明示した統一語彙名）を示すもの（`EncodingObjectNotUsable`。ID は今までどおり `ParameterArgumentTransformationError`）にした。
判定結果と関係の無い `PSCustomObject`（`[pscustomobject]@{ A = 1 }`）にも同じ文を出す（どちらにも合う文にした）。ヘルプの `-Encoding` に書いた。

### 27.3 `Get-ProbedContent -TotalCount` の別名（BUG-0041）

別名 `-Head`・`-First` を付けた（標準の `Get-Content` と同じ）。`-1` を含む負の値は今までどおり受け付けない（7.x の標準と同じ。5.1 の標準は `-1` ですべての行を読む）。
ヘルプの既定値「-1 (unlimited)」を「None (all lines)」に直した（1.1.0 仕様書 4.1・4.5）。

### 27.4 メッセージの細部（BUG-0045）

- **列名の重複:** `Import-ProbedCsv`（12 章）と `Export-ProbedCsv -Append` の追記先（20 章）のメッセージに、ファイルのパスを示す。
  `Import-ProbedCsv -Header` の値が重複している場合は、ファイルのヘッダーではなく `-Header` の値が重複していると分かる文にする（ファイルごとに 1 件）。
  移植したコードは変えず、コマンド側でメッセージだけを差し替える。ID・分類・対象（パス）は今までと同じ
- **`EncodingChangeOnAppend`:** 文字エンコーディングを WebName（`utf-8`・`utf-16`）ではなく統一語彙名（`utf8NoBOM`・`unicodeBOM`・`shift_jis`）で示す。
  追記先の名前は、追記先の BOM の有無を含める。BOM の方針が決まっていない名前（追記では BOM を使わないので指定できる裸の `unicode` など）は WebName で示す
- **繁体字・簡体字中国語の `DetectionVerificationFailed`:** 「以前 N 行判斷」が「以前は」と読めたので、語順を直した（「根據前 N 行判斷 '…' 的字元編碼為 '…'，但檔案含有…」）。
  「以…而言」は、ほかの文（`InvalidSourceBytes` など）と同じまま残した（「對…而言」にそろえるかは今後の課題）
- **英語の行数:** `DetectionLinesTooLarge`・`DetectionVerificationFailed`・`DetectionVerificationIso2022Escape` の「first N lines」は N = 1 で単数・複数が崩れたので、
  3 つとも「the beginning of the file (with -DetectionLineCount N)」に言い換えた（行数による出し分けはしない）

### 27.5 書き込みの失敗のメッセージ

`WriteFailed` のうち、共有違反・ロック違反以外（ディスクの空き不足など）も、読み込みの `FileReadFailed` と同じく、エラー コード（HRESULT）を示す 5 言語のメッセージ（`FileWriteFailed`）にした。
第六次 B までは .NET の例外のまま（7.x では英語、5.1 では OS の言語）だった（26.2）。内部例外は持たせず、HRESULT は引き継ぐ。

## 28. Linux / macOS の既知の制限（リリース前の補足。2026-10-28）

リリースの準備で、WSL の Ubuntu 24.04（.NET 10.0.13、PowerShell 7.6.9）で単体テスト（net10.0）を流し、失敗を仕分けた（実装記録 15 章）。
製品の問題は D1〜D4 の 4 件で、**1.3.0 は 993a341 のモジュールのままリリースし、D1〜D4 は既知の制限として文書に書いて 1.4.0 で直す**（利用者の決定）。どれも元のファイルの内容は失わない。
Windows には当てはまらない。

| # | 内容 | 該当するコマンド | 標準のコマンド（Linux） |
|---|---|---|---|
| D1 | T（1 MiB）を超えるハードリンクに上書きすると、リンクが切れる。書いた名前だけが新しい内容になり、ほかの名前は古い内容のまま。書く内容と元のファイルがどちらも T 以内なら保たれる | `Set-ProbedContent`・`Out-ProbedFile`・`Export-ProbedCsv`・`Convert-ProbedContent` | `Set-Content` はリンクを保つ（同じファイルの往復では 4097 バイトに切り詰める） |
| D2 | 読み込みと追記を別のハードリンク名で行うと、終わらずにファイルが増え続ける（順方向・逆向きとも） | `Add-ProbedContent`（`Get-ProbedContent t.txt \| Add-ProbedContent hard.txt` など） | `Add-Content` も増え続ける（同じ名前でも） |
| D3 | リンク切れのシンボリックリンクへの追記がエラーになる。Windows ではリンクの先に作る（16.5） | `Add-ProbedContent`（`AutoEncodingRequiresExistingFile`）、`Out-ProbedFile -Append`・`Export-ProbedCsv -Append`（`ReadFailed`） | `Add-Content`・`Out-File -Append` は作る。`Export-Csv -Append` はエラー |
| D4 | 共有を許さずに開かれたファイル（.NET の `FileShare.None`。Linux の .NET は `flock` の勧告ロックで表す）のメッセージが「error code 0x0000000B」になる。ID（`ReadFailed`・`WriteFailed`）は正しい（26.2） | 読み書きのすべて | 「being used by another process」 |

- **macOS は、ハードリンクの扱い（D1・D2）を確かめていない。** 同じファイルの判定は Linux と同じくリンクを解決したパスで比べる（16.5）ので、D2 は同じく起きると考えられる
- **`LANG` が未設定（不変カルチャー）の Linux では、カルチャーによる絞り込みが効かない。** 不変カルチャーは東アジアのカルチャーではないので、1.2.0 のカルチャーゲートで旧マルチバイトの独自判定を打ち切る。
  日本語のファイルは、クラスライブラリの独自判定では `-1`、`Resolve-Encoding`（`Combined`）では UTF.Unknown の結果（Shift_JIS は `932 / shift-jis`、EUC-JP は `51932 / euc-jp`）になる。
  Windows で形式を英語（米国）や不変カルチャーにした場合と同じ結果で、設計どおり。`-Culture ja-JP` を指定するか、`LANG=ja_JP.UTF-8` などを設定するよう案内する（README）
- **Linux では、`Export-ProbedCsv -Append` が追記先の CRLF を引き継ぐ**（16.3）ため、LF を書く標準の `Export-Csv -Append` と違う（21 章の表）。
  Windows では両方が CRLF なので一致する。仕様どおりで、直さない
- 原因・直し方の案・規模は実装記録 15 章。テストを Linux・macOS でも動くようにすることも 1.4.0 の候補にした
