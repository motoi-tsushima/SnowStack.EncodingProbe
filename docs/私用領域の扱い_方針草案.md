# 私用領域（外字）の扱い

- 作成日: 2026-09-21
- 状態: 草案
- 対象: SnowStack の文字エンコーディング処理（EncodingProbe、rmsmf、mfsr）

以下、これらに共通する文字エンコーディング処理を「本処理」と呼ぶ。

---

## 1. 方針

本処理は、`System.Text.Encoding` の意味論に従う。
文字エンコーディングの解釈、Unicode との対応づけ、変換できない文字の扱いは、
.NET の実装が定めるものをそのまま用い、本処理が独自の解釈を加えることはない。

この原則に基づき、本処理は私用領域に写されるバイト列に**介入しない**。
判定・復号・符号化のいずれにおいても、`System.Text.Encoding` の既定の動作を
そのまま利用者に渡す。意味の解釈は利用者に委ねる。

WHATWG Encoding Standard のように、これらのバイト列を
特定の文字集合（HKSCS 等）へ写し替える解釈は採用しない。

---

## 2. 背景

### 2.1 規格が文字を定めていないバイト列

旧マルチバイト文字エンコーディングには、規格として文字を定めていない領域がある。
本処理が扱う範囲では 2 種類ある。

**(a) ユーザー定義領域**
利用者が独自の文字を割り当てるために空けてある 2 バイトの領域。
日本語では外字、繁体字中国語では造字、規格上は EUDC
（End-User-Defined Characters）と呼ばれる。

**(b) 未定義の単バイト**
規格として何も割り当てられていない単バイト。

### 2.2 私用領域への写像

`System.Text.Encoding` は、これらのバイト列を Unicode の私用領域
（Private Use Area, U+E000–U+F8FF）へ**位置順で機械的に**写す。
例外も置換文字も発生しない。

| 文字エンコーディング | バイト列 | 符号位置 |
|---|---|---|
| CP932 | F0 40 から | U+E000 から |
| CP950 | FA 40 → FA 5F | U+E000 → U+E01F |
| CP950 | 81 40 → 88 62 | U+EEB8 → U+F325 |

未定義の単バイトは、コードページごとに異なる符号位置へ割り当てられている。

| コードページ | バイト | 符号位置 |
|---|---|---|
| 932 | A0, FD, FE, FF | U+F8F0–U+F8F3 |
| 936 | FF | U+F8F5 |
| 949 | FF | U+F8F7 |
| 950 | FF | U+F8F8 |
| 20932 / 51932 | A0, FF | U+F8F0, U+F8F3 |
| 51949 | A0, AD, AE, AF, FE, FF | U+F8E6–U+F8EB |

割り当て先がコードページごとに重複しないよう分けられていることから、
この仕組みが往復の保存を目的としたものであることがわかる。

### 2.3 私用領域の意味

私用領域は、Unicode が意味を定めない領域である。
「どの字か」を決めるのはバイト列の外側にある取り決め
（フォント・入力環境・地域の慣行）であり、符号化されたデータには含まれない。

したがって、同じ U+F325 が香港では HKSCS のある字、台湾では Big5-UAO の別の字、
別の環境では独自の造字を意味しうる。
私用領域へ写されたという事実は「同定できなかった」ことを意味する。

---

## 3. 判定への影響

私用領域に写されるバイト列の出現を、文字エンコーディング判定の材料としない。

判定処理はこれらのバイト列を、その文字エンコーディングとして「規格内」と扱う。
除外の材料にも、特定の変種（HKSCS など）を選ぶ材料にもしない。

2.3 に述べたとおり、私用領域は同定できなかったことを意味するため、
そこから産地や変種を推し量ることは原理的にできない。

---

## 4. 復号・符号化での扱い

| 場面 | 動作 |
|---|---|
| 読み込み | 私用領域の符号位置としてそのまま返す。警告・エラーは出さない |
| 書き込み | 私用領域の符号位置を、元のバイト列へそのまま戻す |

### 4.1 コードページごとの可逆性

2 章に述べたバイト列が私用領域へ写され、同じバイト列へ戻るかどうかは、
コードページによって異なる。

| コードページ | 文字エンコーディング | ユーザー定義領域の扱い | 可逆性 |
|---|---|---|---|
| 932 | Shift_JIS（Windows-31J） | 私用領域へ写す | 可逆 |
| 20932 | EUC-JP | 私用領域へ写す | 可逆 |
| 51932 | EUC-JP（CP51932） | `・`（U+30FB）へ置換 | **非可逆・検出不能** |
| 936 | GBK | 私用領域へ写す | 可逆 |
| 51936 | EUC-CN | 私用領域へ写す | 可逆 |
| 54936 | GB18030 | 私用領域へ写す | 可逆 |
| 949 | 統合ハングル（CP949） | 私用領域へ写す | 可逆 |
| 51949 | EUC-KR | `?` へ置換 | 非可逆・検出可能 |
| 950 | Big5（CP950） | 私用領域へ写す | 可逆 |

「可逆」としたコードページでは、
バイト列→符号位置→バイト列、符号位置→バイト列→符号位置の双方向で、
往復失敗 0 件を確認している（検証方法は付録 A）。

したがって、これらのコードページのファイルを読み込み、
加工せずに同じ文字エンコーディングで書き戻した場合、
外字を含むファイルであってもバイト列は保存される。

コードページ 51950（EUC-TW）は、.NET の実行環境が提供していないため、
復号・符号化ともに行えない。

### 4.2 日本語 EUC の 2 つのコードページ

日本語の EUC には 20932 と 51932 の 2 つがあり、どちらも `euc-jp` を名乗る。
`Encoding.GetEncoding("euc-jp")` が返すのは 51932 である。

両者は、規格外のバイト列の扱いが異なる。

| バイト列 | cp20932 | cp51932 |
|---|---|---|
| F5 A1（ユーザー定義領域） | U+E000 → F5 A1（可逆） | U+30FB → A1 A6（非可逆） |
| 8F B0 A1（SS3 を含む列） | U+008F U+4E9C → 8F B0 A1（可逆） | U+30FB U+4E9C → A1 A6 B0 A1（非可逆） |

cp51932 は、これらのバイト列を実在する文字（U+30FB `・`）へ置換する。
置換結果が通常の文字であるため、復号結果から異常を検出できない。
この置換は、8.2 に述べる読み込み時のフォールバックによるものである。

なお、どちらのコードページも JIS X 0212（補助漢字）を解釈しない。
cp20932 は SS3（`8F`）を制御文字としてそのまま返すため、
補助漢字としては読めないが、バイト列は保存される。

### 4.3 不正なバイト列との区別

構造的に不正なバイト列は、これとは別の扱いとなる（8.2 のフォールバックにより
置換される）。規格が文字を定めていない領域は「未定義の文字」であって
「不正なバイト列」ではない。

---

## 5. 本処理が行わないこと

- 私用領域の符号位置を、実在の Unicode 符号位置へ写し替えない
- HKSCS・Big5-UAO・倚天拡張などの対応表を同梱しない
- 私用領域に写されるバイト列を含むという理由で、判定結果や文字エンコーディング名を変えない
- 私用領域の符号位置の存在を理由に、警告・エラーを出さない

---

## 6. 利用者側での対処

意味としての解釈が必要な場合は、復号後の文字列に対して利用者が写像を行う。
本処理はバイト列を保存するため、この後処理は利用者の責任範囲で行える。

### 6.1 例

Shift_JIS の外字領域に社内の造字を割り当てて運用してきたファイルを、
UTF-8 へ移行する場合を示す（EncodingProbe を用いた例）。

```powershell
# 利用者が保有する外字対応表（符号位置 → 本来の文字）
$gaiji = @{ 0xE000 = '𠮷'; 0xE001 = '髙' }

$text = Get-ProbedContent .\customers.txt -Raw

# 私用領域の符号位置が含まれるかの確認
if ($text -match '[\uE000-\uF8FF]') { '外字が含まれています' }

# 利用者の表で写し替える
$fixed = -join ($text.ToCharArray() | ForEach-Object {
    $cp = [int]$_
    if ($gaiji.ContainsKey($cp)) { $gaiji[$cp] } else { $_ }
})

$fixed | Set-ProbedContent .\customers_utf8.txt -Encoding utf8NoBOM
```

この処理が成立するのは、本処理が私用領域の符号位置をそのまま返すためである。
置換文字にしたり例外を投げたりしていれば、利用者は表を引く手掛かりを失う。

対応表は環境ごとに異なり、U+E000 が何を意味するかを知るのは利用者だけである。
本処理が対応表を同梱しないのは、機能の不足ではなく、知りえないためである。
香港の HKSCS についても同様で、利用者が表を保有していれば
上記の `$gaiji` を差し替えるだけで同じ処理が成立する。

### 6.2 写し替えは一方向である

写し替えた文字列を元の文字エンコーディングへ書き戻しても、
元のバイト列は再現されない。6.1 の例を CP932 へ書き戻すと、次のようになる。

| 元のバイト列 | 写し替え後 | CP932 へ書き戻した結果 | 見え方 |
|---|---|---|---|
| F0 40 | `𠮷` | 3F 3F（`??`） | 壊れたことが分かる |
| F0 41 | `髙` | FB FC（IBM 拡張文字の位置） | **正しく見えるが、元の位置ではない** |

`𠮷` は CP932 に存在しないため `?` になる（サロゲートペアのため 2 つ）。
`髙` は CP932 の IBM 拡張文字として存在するため、外字領域ではなくその位置へ書かれる。
後者は文字としては正しいが、バイト列は元と異なる。

意味の獲得とバイト列の保存は両立しない。
どちらを採るかの判断を利用者に残すことが、1 章の方針の目的である。

---

## 7. 限界

- 私用領域の符号位置は、対応するフォントが無い環境では字形を持たない
- 私用領域を含む文字列を他の文字エンコーディングへ変換した場合、
  符号位置は保存されるが、意味は依然として環境依存のままである
- 本処理は、私用領域の符号位置が含まれることを利用者に通知しない。
  必要な場合は 6.1 の方法で利用者が検出する
- 将来、特定の文字集合に基づく写像を提供する場合は、明示指定による
  オプトインとし、既定の動作は変更しない

---

## 8. 存在しない文字の扱い（フォールバック）

本処理は、文字エンコーディングに存在しない文字・解釈できないバイト列の扱いにも
介入しない。`System.Text.Encoding` の既定の動作に従う。

### 8.1 書き込み時

変換先の文字エンコーディングに存在しない文字は、コードページにより
次のいずれかとなる。

| コードページ | 動作 | 例 |
|---|---|---|
| 20127（US-ASCII）など | `?` へ置換 | `é` → `?` |
| 932 などの旧マルチバイト | 似た文字へ置換（ベストフィット）。無ければ `?` | `é` → `e` |

ベストフィットによる置換は、書き込み結果から検出できない。
BMP 外の文字（サロゲートペア）は、`?` 2 つとなる。

### 8.2 読み込み時

解釈できないバイト列は、コードページにより `?` または別の文字へ置換される。
日本語のコードページでは `・`（U+30FB）となる場合がある（4.2 の cp51932 の例）。

### 8.3 私用領域との関係

私用領域の符号位置は、それを持つコードページへ書き込む場合、
ベストフィットの対象とならない（似た文字が存在しないため）。
4.1 の可逆性は、この性質に依拠している。

私用領域を持たないコードページへ書き込む場合は `?` となる。
たとえば日本語の外字（U+E000）を cp949 へ書き込むと `?` になる。

### 8.4 置換を避けるには

置換が許容できない場合は、変換先を UTF-8 などの Unicode 系文字エンコーディングにする。
Unicode 系ではすべての文字が表現できるため、置換は起きない。

## 9. ツール別の補足

### 9.1 EncodingProbe

- 日本語の EUC を検出した場合、判定結果としてコードページ **20932** を返す。
  4.2 に述べた可逆性を保つためである
- 判定結果の `EncodingWebName` は `Encoding.WebName` をそのまま返すため、
  20932 に対して `euc-jp` となる。この名前で `Encoding.GetEncoding` を呼ぶと
  51932 が返る。往復を保証するのは `CodePage` であり、`EncodingWebName` ではない
- `Get-ProbedContent` の結果を加工せずに `Set-ProbedContent -EncodingFrom` で
  書き戻した場合、4.1 で「可逆」としたコードページではバイト列が保存される
- `-Encoding` で 51932 を明示指定した場合は、4.2 の置換が起きる。
  本処理はこれに介入しない
- 51950 が判定された場合、または明示指定された場合は、
  `CodePageNotAvailable` として報告する

## 付録 A. 検証方法

以下の 2 つの検査を、次の環境で実行した。

- Windows 11（PowerShell 5.1 / 7.6.6）
- Ubuntu 24.04（PowerShell 7.6.5）
- macOS 15.7（PowerShell 7.6.4）

4 環境すべてで、件数を含め同一の結果を得た。
4.2 の 20932 / 51932 の比較は、Windows 11 の PowerShell 5.1 / 7.6.6 で確認した。

### A.1 バイト列側からの往復

```powershell
foreach ($cp in 932, 950, 949, 936) {
    $e = [Text.Encoding]::GetEncoding($cp)
    $ng = 0; $total = 0
    foreach ($l in 0x81..0xFE) { foreach ($t in 0x40..0xFE) {
        $b = [byte[]]($l, $t); $s = $e.GetString($b)
        if ($s.Length -eq 1 -and [int][char]$s -ge 0xE000 -and [int][char]$s -le 0xF8FF) {
            $total++
            if ([BitConverter]::ToString($e.GetBytes($s)) -ne [BitConverter]::ToString($b)) { $ng++ }
        }
    } }
    "cp{0}: PUA {1} 件中 往復失敗 {2} 件" -f $cp, $total, $ng
}
```

| コードページ | 私用領域へ写る 2 バイト列 | 往復失敗 |
|---|---|---|
| 932 | 1880 | 0 |
| 936 | 2149 | 0 |
| 949 | 188 | 0 |
| 950 | 6217 | 0 |

### A.2 符号位置側からの往復

```powershell
$codePages = 932, 936, 949, 950, 20932, 51932, 51936, 51949, 51950, 54936

foreach ($cp in $codePages) {
    try { $e = [Text.Encoding]::GetEncoding($cp) }
    catch { "cp{0}: 実行環境が提供していない" -f $cp; continue }

    $total = 0; $ng = 0; $skip = 0
    foreach ($u in 0xE000..0xF8FF) {
        $c = [char]$u
        $b = $e.GetBytes([string]$c)
        if ($b.Length -eq 1 -and $b[0] -eq 0x3F) { $skip++; continue }
        $total++
        $back = $e.GetString($b)
        if ($back -ne [string]$c) { $ng++ }
    }
    "cp{0,-6}: PUA {1,4} 件中 往復失敗 {2} 件（符号化不可 {3} 件）" -f $cp, $total, $ng, $skip
}
```

| コードページ | 符号化できる符号位置 | 往復失敗 |
|---|---|---|
| 932 | 1884 | 0 |
| 936 | 2150 | 0 |
| 949 | 189 | 0 |
| 950 | 6218 | 0 |
| 20932 | 1882 | 0 |
| 51932 | 2 | 0 |
| 51936 | 2150 | 0 |
| 51949 | 6 | 0 |
| 51950 | 実行環境が提供していない | — |
| 54936 | 6400 | 0 |

A.1 と A.2 の件数の差は、2.2 に示した未定義の単バイトによる。
51932 と 51949 の件数が少ないのは、ユーザー定義領域を私用領域へ写さず、
未定義の単バイトのみが私用領域に対応しているためである。
