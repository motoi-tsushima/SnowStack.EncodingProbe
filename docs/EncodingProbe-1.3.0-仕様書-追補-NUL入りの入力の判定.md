## 2. 判定処理の変更

### 2.1 変更する箇所

`EncodingDetector.Detection` の判定順序（CLAUDE.md「判定パイプライン」の 1〜6）は変えない。
**3（ISO-2022 / ASCII）で ASCII と判定した場合の扱いだけ**を、次のように変える。

1. `ISO2022_Detection` が **ASCII**（ESC シーケンスが無く、すべてのバイトが `0x80` 未満）と答え、**かつ入力に `0x00` が 1 つ以上ある**場合だけ、2.2 の厳密な検査を行う
2. 2.2 のどれかが成立したら、そのコードページを結果とする（BOM は無し）
3. どれも成立しなければ、**従来どおり ASCII（20127）を結果とする。UTF-8 の判定には進まない**

次の場合は、従来の経路をそのまま通る（結果は一切変わらない）。

- `ISO2022_Detection` が ISO-2022 と答えた場合（ESC シーケンスがある）
- `0x00` が無い場合
- `0x80` 以上のバイトがある場合（ISO-2022 / ASCII の判定を通らない）
- BOM がある場合（BOM で確定する）

### 2.2 厳密な検査

**既存の `Utf32_Detection` / `Utf16_Detection` は使わない。** 調査報告 4.2 のとおり、この分岐の前提（すべてのバイトが `0x80` 未満）では、
既存の UTF-16 の判定はほぼ常に成立してしまうためである。

入力を先頭（オフセット 0）から単位に区切り、次の表の順に、**すべての単位**が形に合うかを調べる。

| 順 | 結果 | 長さの条件 | 各単位の形 |
|---|---|---|---|
| 1 | UTF-32LE（12000） | 4 の倍数（4 以上） | `<00 以外> 00 00 00` |
| 2 | UTF-32BE（12001） | 4 の倍数（4 以上） | `00 00 00 <00 以外>` |
| 3 | UTF-16LE（1200） | 偶数（2 以上） | `<00 以外> 00` |
| 4 | UTF-16BE（1201） | 偶数（2 以上） | `00 <00 以外>` |
| 5 | ASCII（20127） | — | 1〜4 のどれにも当てはまらない |

- 「`00` 以外」の側のバイトは、この分岐の前提によりすべて `0x01`〜`0x7F` である。制御文字も受け入れる（絞り込まない）
- 英数字（U+0001〜U+007F）だけの BOM 無し UTF-16 / UTF-32 は、必ずこの形になる。`0x00` を含む ASCII のテキストは、ほとんどの場合この形にならない
- 実装は、調査報告 7.1.1 の差分（`StrictNulUnicode_Detection` / `AllStrictUnits`）を手本にしてよいが、名前・コメント・置き場所は既存のコードのスタイルに合わせて書き直す。「【実験】」の表記は残さない

### 2.3 結果の各プロパティ

| プロパティ | 値 |
|---|---|
| `CodePage` | 2.2 の表の値 |
| `Bom` | `false` |
| `EncodingWebName` / `PSEncodingName` / `UsePSName` | 既存の規則（`EncodingName` / `PSEncodingName` / `SetUsePSName`）でコードページから決める。BOM 無しの UTF-16 / UTF-32 を判定した既存の経路と同じ値になること |
| `LineBreak` | 変えない（`DetectLineBreak` の結果のまま）。2.2 が成立する入力では、改行は UTF-16 / UTF-32 の形で数えられる（調査報告 2.1 の `LineBreak` 列のとおり） |
| `Culture` | 変えない |

### 2.4 判定方式・カルチャー・TFM

- `Combined` と `NativeOnly` の両方で効く（独自判定の中の変更であるため）。UTF-16 / UTF-32 は旧マルチバイトではないので、UTF.Unknown との突き合わせは起きない
- `UtfUnknownOnly` は変わらない（独自判定を通らない）
- カルチャーには依存しない（判定順序 1〜4 はカルチャーに関わらず実行される）
- net48 と net10.0 で同じ結果になること

### 2.5 公開 API

クラスライブラリの公開 API（型・メソッド・プロパティ）は変えない。変わるのは、上の入力に対する判定の結果だけである。

## 4. 既知の限界

次の 3 点は直さない。1.3.0 仕様書・README・ヘルプ（`Resolve-Encoding` の NOTES）に記載する。

### 4.1 2 バイトとも `0x80` 未満になる文字を含む UTF-16 / UTF-32

英数字の中に、UTF-16 の 2 バイトがともに `0x01`〜`0x7F` になる文字（「上」U+4E0A = `0A 4E`、「字」U+5B57、「あ」U+3042、「、」U+3001 など）が混じった BOM 無しの UTF-16 / UTF-32 は、
2.2 の形にならないので、**従来どおり ASCII と判定される。**

- 修正前より悪くはならない（修正前も ASCII と判定されていた）
- **`Import-ProbedCsv` / `Export-ProbedCsv` の `-DetectionLineCount` を指定すると、正しく読める。** 切り出しで決めた改行の型（UTF-16 / UTF-32）による読み替え（1.3.0 仕様書 3.2・U4）が働くためである。ヘルプでこの方法を案内する
- `0x80` 以上のバイトになる文字（ほとんどの日本語の文字など）を 1 つでも含むファイルは、この限界に当たらない（ISO-2022 / ASCII の判定を通らず、既存の UTF-16 / UTF-32 の判定で正しく判定される）

### 4.2 数バイトの入力

`41 00` のような数バイトの入力は、「BOM 無しの UTF-16LE の `A`」とも「ASCII の `A` と終端の `00`」とも読め、バイト列からは区別できない。
2.2 の形に合えば UTF-16 / UTF-32 と判定する（`41 00` → UTF-16LE、`41 00 00 00` → UTF-32LE、`41 00 42 00 43 00` → UTF-16LE など）。

### 4.3 U+0000 の文字を含む UTF-16 / UTF-32

英数字だけの BOM 無し UTF-16 / UTF-32 でも、U+0000 の文字（`00 00` の単位）を含むものは 2.2 の形にならず、ASCII と判定される（調査報告の A6-4）。

## 5. PowerShell モジュール 1.3.0 への影響

| 項目 | 影響 |
|---|---|
| `Resolve-Encoding`（全体・`-DetectionLineCount`） | 英数字だけの BOM 無し UTF-16 / UTF-32 に、`us-ascii` ではなく UTF-16 / UTF-32 を報告する |
| `Get-ProbedContent` など全体で判定するコマンド | 英数字だけの BOM 無し UTF-16 / UTF-32 を正しく読む（`U+0000` が混じらない） |
| `Import-ProbedCsv` / `Export-ProbedCsv`（全体で判定） | 同上 |
| `-DetectionLineCount` の読み替え（1.3.0 仕様書 3.2） | 英数字だけの UTF-16 / UTF-32 は、判定の時点で UTF-16 / UTF-32 になるので、読み替えの UTF-16 / UTF-32 の行を通らない。**読み替えは 4.1 の入力のために残す** |
| 1.3.0 仕様書 3.3（3 つのコマンドの判定結果の一致） | 変わらない（同じクラスライブラリの判定を使うため） |
