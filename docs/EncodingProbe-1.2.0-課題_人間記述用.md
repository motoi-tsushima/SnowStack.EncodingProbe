# 1.2.0 の課題 - 人間が記述する文書

- 起票日: 2026-09-01
- 対象: `SnowStack.EncodingProbe.PowerShell`（コマンドレット側）
- 状態: 課題 1 は **対応済み**（2026-09-10）。

## 課題 1:ドイツ語などに対応が不十分

### 現象

文字エンコーディング検出処理全般で、ドイツ語などの旧シングルバイト文字エンコーディング圏における旧シングルバイト文字エンコーディングテキストを対象としたとき、`-Strategy`オプション で`UtfUnknownOnly`を指定しないと、旧シングルバイト文字エンコーディングを正しく検出できない。 `shift_jis`と誤検出してしまう場合がある。

### 原因

`Resolve-Encoding` などコマンドレットでは`EncodingProbe.Detect`を使用しており、これらはまず`Unicode`の検出確認を終えたあとで、`Shift_JIS`や`CP949`など東アジアの旧マルチバイト文字の検出処理を行う。

それらの検出処理が全て該当しなかった場合に、`UTF.Unknown` に検出処理を任せる。

ドイツ語など旧シングルバイト文字エンコーディング圏では、東アジアの旧マルチバイト文字の検出処理自体が不必要であるだけでなく、誤検出の原因となる。

### 対策

`SnowStack.EncodingProbe`クラスライブラリは、カルチャー情報を取得する。コマンドレットがどの国の言語で稼働しているか、実行時には知っている。

内部で、`SnowStack.EncodingProbe`クラスライブラリの `Detect`メソッド（文字エンコーディング解析処理）を呼び出しているコマンドレット全てに対して、「東アジアの旧マルチバイト文字を使用しているカルチャー」では**無い**場合は、東アジアの旧マルチバイト文字の**検出処理をスキップする**必要がある。

旧シングルバイト文字エンコーディング圏では、ASCIIか否か・Unicodeか否かの検出だけできれば良い。

カルチャー情報で検出処理を分岐する改修が必要です。

### Claude用記載欄

**対応済み**（2026-09-10、ブランチ `feature/1.2.0-world-language-detection`）。

#### 調査でわかったこと

依頼された「カルチャーによる判定のスキップ」は、**すでに半分は実装されていた**。
`EUCxx_Detection` は `GetEucCodePageFromCulture()` が -1 を返した時点で、
`CPxxx_Detection` は該当するカルチャーが無い時点で、それぞれ判定をスキップしていた。
実測でも `-Culture de-DE` を指定すると独自判定は -1 を返し、
既定の判定方式の結果は `-Strategy UtfUnknownOnly` と同じだった。

実際に起きていた誤判定は**逆方向**だった。
テストレポートを採取した実行環境は `CurrentCulture = ja-JP` である。
日本語カルチャーの実行環境でドイツ語の windows-1252 のファイルを読むと、
`FC DF`（`üß`）が Shift_JIS の外字領域の 2 バイト文字として構造が成立してしまい、
独自判定が Shift_JIS と主張する。独自判定が先に答えを返すため UTF.Unknown の出番が無い。
韓国語カルチャーなら CP949、簡体字中国語なら GB18030、繁体字中国語なら Big5 と、
同じことがそれぞれのカルチャーで起きる。

もう 1 件、カルチャーに依存しないバグも見つかった。
`Utf8_Detection` が、多バイト文字の後続バイトが足りないまま ASCII に戻った場合に
それを見逃していた。そのため windows-1252 のフランス語（`46 72 61 6E E7 61 69 73` = `Français`）を
UTF-8 と誤判定していた。.NET の厳格な UTF-8 デコーダーはこのバイト列を復号できない。

#### 行った修正

1. **カルチャー語彙の集約とゲートの明示**（`EncodingDetector.cs`）
   `EastAsianLegacyRegion` 列挙型と `GetEastAsianLegacyRegion()` を追加し、
   カルチャー名と判定対象の対応表を 1 か所にまとめた。
   `IsChineseSimplifiedCulture()` は廃止し、`GetEucCodePageFromCulture()` と
   `CPxxx_Detection()` もこの結果で分岐するようにした。
   `Detection()` は、カルチャー圏が `None` なら旧マルチバイトの判定に入らず判定不能で返す。
   BOM・ISO-2022・ASCII・UTF-32・UTF-16・UTF-8 はこれより手前にあるため、
   カルチャーに関わらず実行される（UTF.Unknown が BOM 無しの UTF-16 / UTF-32 に
   対応していないため、Unicode 系を落とすわけにはいかない）。

2. **統合層でのクロスチェック**（`EncodingProbe.cs`）
   既定の判定方式（`Combined`）で、独自判定が旧マルチバイトのコードページ
   （932 / 936 / 949 / 950 / 20932 / 51936 / 51949 / 51950 / 54936）を返した場合は、
   UTF.Unknown にも判定させ、UTF.Unknown がシングルバイト文字エンコーディングと
   判定していればそちらを採用する。
   本物の東アジアのテキストに対して UTF.Unknown が返すのはマルチバイトの符号化か
   判定不能なので、既存の判定結果は変わらない。
   `-Strategy NativeOnly` はこの突き合わせを行わない（独自判定だけを見たい用途のため）。

3. **UTF-8 判定の厳密化**（`EncodingDetector.Utf8_Detection`）
   RFC 3629 の整形式バイト列の表どおりに検証するよう書き直した。
   途中で途切れた多バイト文字、冗長な符号化、サロゲート符号位置、
   U+10FFFF を超える符号位置を、いずれも規格外とする。

#### 結果

テストデータのドイツ語 windows-1252 を、既定の判定方式で 10 のカルチャーから判定した結果:

| カルチャー | 修正前 | 修正後 |
|---|---|---|
| de-DE / fr-FR / ru-RU / en-US など | 28591 (iso-8859-1) | 28591 (iso-8859-1) |
| ja-JP | **932 (shift_jis)** | 28591 (iso-8859-1) |
| ko-KR | **949 (cp949)** | 28591 (iso-8859-1) |
| zh-CN | **54936 (gb18030)** | 28591 (iso-8859-1) |
| zh-TW | **950 (big5)** | 28591 (iso-8859-1) |

ロシア語 (cp1251 / KOI8-R)、ポーランド語 (cp1250 / ISO-8859-2)、タイ語 (cp874)、
フランス語 (cp1252 / ISO-8859-15) も、どのカルチャーでも同じ結果になり、
復号した本文が元の本文と一致することを確認した。

#### 検証

- xUnit: net10.0 412 件 / net48 422 件、PowerShell 側 432 件、すべて成功
  （新規 `WorldLanguageTests` / `Utf8StrictnessTests` を含む）
- PSCompat: 285 シナリオで PowerShell 5.1 と 7.x の結果が完全に一致
- 既存の日本語・韓国語・繁体字中国語・簡体字中国語のテストは 1 件も変わっていない

#### 残した課題

- 独自判定そのものに妥当性の観点（検出した 2 バイト文字が外字領域に偏っていないか等）は
  入れていない。`-Strategy NativeOnly` は依然として日本語カルチャーでドイツ語を
  Shift_JIS と判定する。既定の判定方式では上記のクロスチェックで救済される
- UTF.Unknown 自身の判定精度は本改修の対象外である。
  短いフランス語やスペイン語のファイルで UTF.Unknown が別のシングルバイト符号化を
  返す（あるいは判定不能になる）ことがあるが、これは UTF.Unknown の担当範囲である
