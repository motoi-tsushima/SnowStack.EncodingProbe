## 1. `PSEncodingName` の `I do not know.` を null にする

### 1.1 現象

PowerShell のフレンドリ名が存在しないエンコーディングを判定すると、`PSEncodingName` に `I do not know.` という文字列が入る。

```
PS> Resolve-Encoding w1252_sub.txt

CodePage        : 1252
EncodingWebName : windows-1252
PSEncodingName  : I do not know.
UsePSName       : False
```

28591（iso-8859-1）でも同じだった。1.1.0 仕様書 4.4 節は、この場合 `PSEncodingName` を「設定しない（null）」と定めている。

### 1.2 修正内容

- フレンドリ名が無い場合の `PSEncodingName` を **null** にする（空文字列ではない）。`UsePSName` は従来どおり false
- `I do not know.` を設定している箇所をすべて特定して直す。判定結果の組み立て以外（既定値、ヘルプ、サンプル、テストの期待値など）に同じ文字列があれば、それも直す
- `PSEncodingName` は PowerShell コマンドレット固有の値であり、mfsr / mfprobe などの他のツールへの影響は考慮しなくてよい（それらの側が後で合わせる）
- 修正は**無条件に行ってよい**。事前の報告は不要

### 1.3 記録すること

- 発生箇所（ファイル・型・メソッド）と、公開済みの 1.1.0 に含まれていたか（含まれていた場合、どのバージョンからか）を実装記録に書く
- `CHANGELOG.md` に「不具合の修正」として記載する（1.1.0 以前から存在した場合はその旨も）

### 1.4 テスト

- フレンドリ名の無いコードページ（1252、28591、20932、950 など）で `PSEncodingName` が null、`UsePSName` が false であること
- フレンドリ名のあるもの（UTF-8、UTF-16LE など）は従来どおりであること
- PSCompat で PS 5.1 / 7.x の両方で確認する（PS 5.1 と 7.x ではフレンドリ名の有無が異なるものがある。その違いは従来どおり）

## 2. `-WhatIf` で、実行すれば失敗するエラーを報告する

### 2.1 方針

**「ファイルを変更しない検査で失敗するもの」は、`-WhatIf` のときにも報告する。** そのために、そうした検査を `ShouldProcess` の呼び出しより前に置く。

- エラーの分類（終了エラー / 非終了エラー）は変えない。`Out-ProbedFile` は終了エラー、他の 3 コマンドは非終了エラーのまま
- `-Confirm` のときは、検査で失敗するファイルについて確認を求めない（検査が先に失敗するため。自然にそうなる）
- ファイルの内容を変更する処理は、従来どおり `ShouldProcess` の後にだけ行う

### 2.2 対象

| コマンド | `ShouldProcess` より前に置く検査 |
|---|---|
| `Out-ProbedFile` | `-NoClobber` で出力先が存在する、読み取り専用で `-Force` なし |
| `Set-ProbedContent` / `Add-ProbedContent` | 読み取り専用で `-Force` なし（ほかにも、ファイルを変更せずに判定できる失敗があれば同様） |
| `Convert-ProbedContent` | N6（読み取り専用・書き込み権限）、N7（出力先に同名ファイル）、N8（同じ実行での名前の重なり）、N9（出力先が変換元と同じ） |

まず 4 コマンドの現状の順序を調べ、そろっていないものだけを直すこと。調査結果は実装記録に書く。

注意点:

- `Convert-ProbedContent` の N8 は、`-WhatIf` では実際には何も書かれない。その場合も、**書く予定のファイル名を記録して**重なりを検出すること（`-WhatIf` と通常の実行で同じエラーが出るように）
- `Out-ProbedFile` の `-Append` の整合性検査（バイト列比較）は、入力が届くまで判定できないため対象外（従来どおり）
- 「書き込み権限なし（読み取り専用以外の理由）」は、実際に開くまで分からない場合は対象外でよい

### 2.3 文書

- 1.2.0 仕様書 2.10 節（`BeginProcessing` での検査の順序）と 2.14 節を改める。`ShouldProcess` を `-NoClobber`・読み取り専用の検査の後ろに移す
- 1.2.0 仕様書 15.1 節・16 章に、`Convert-ProbedContent` の `-WhatIf` で報告されるエラー（N3・N4 は従来どおり、加えて N6〜N9）を明記する
- 実装記録 2.6 に「手動確認の結果、2026-09-29 に方針を改めた」旨と改めた内容を追記する（元の記述は消さない）
- `Set-ProbedContent` / `Add-ProbedContent` の挙動が変わった場合は、`CHANGELOG.md` に記載する

### 2.4 テスト

- 各コマンドで、2.2 の表の各事象について `-WhatIf` でエラーが報告され、ファイルが変更されないこと
- `-WhatIf` なしの場合と同じ `FullyQualifiedErrorId` であること
- 検査に通るファイルは、従来どおり `-WhatIf` のメッセージが出て何も書かれないこと

## 3. `Convert-ProbedContent -PassThru` に `SourceCodePage` を追加する

### 3.1 背景

1.2.0 仕様書 17 章は「出力された名前（`SourceEncoding`）をそのまま `-Encoding` に渡せば元に戻せる」としていた。
これは EUC-JP で成り立たない。判定結果が 20932 のとき `SourceEncoding` は `euc-jp` になるが、`euc-jp` を `Encoding.GetEncoding` に渡すと 51932 が返る。
1.1.0 仕様書 4.4 節の「往復を保証するのは `CodePage` であり、`EncodingWebName` ではない」と矛盾していた。

### 3.2 追加するプロパティ

| プロパティ | 型 | 内容 |
|---|---|---|
| `SourceCodePage` | `int` | 変換元のコードページ番号（判定結果の `CodePage`、または `-SourceEncoding` で指定したもののコードページ） |

- `SourceEncoding` の直後に置く
- 変換元が 0 バイトの場合は、実装記録 2.4 の現状の扱い（変換元とみなしたエンコーディング）のコードページとする（5 章で明文化する挙動と一致させる）
- 変換先のコードページ（`CodePage`）は追加しない

### 3.3 往復の案内

1.2.0 仕様書 17 章と、`Convert-ProbedContent` のヘルプ（5 言語）に、次の趣旨を書く。

- 元に戻すには、**Unicode 系は `SourceEncoding`**（`utf8BOM` など、BOM の有無まで表す明示形）、**それ以外は `SourceCodePage`** を `-Encoding` に渡す
- `SourceEncoding` の WebName は、別のコードページに解決される場合がある（`euc-jp` は 51932 になる）。Unicode 系以外で `SourceEncoding` を渡すと、元に戻らないことがある

例:

```powershell
$r = Convert-ProbedContent .\a.txt -Encoding utf8NoBOM -PassThru
Convert-ProbedContent .\a.txt -Encoding $r.SourceCodePage    # Unicode 系以外の場合
```

### 3.4 テスト

- EUC-JP（20932 と判定される既存のテストデータ）を `utf8NoBOM` に変換し、`-Encoding $r.SourceCodePage` で戻すと、元のバイト列に一致すること
- 同じ入力で `SourceEncoding` が `euc-jp`、`SourceCodePage` が 20932 であること
- Shift_JIS、Big5（HKSCS を含む `Chinese_HongKong/sample_big5hkscs.txt`）、windows-1252 でも `SourceCodePage` で往復すること
- Unicode 系（UTF-8 BOM 付き、UTF-16LE BOM 無し）は `SourceEncoding` で往復すること

## 4. シングルバイト系の判定の限界を文書化する

### 4.1 背景（手動確認の結果）

イタリア語の windows-1252 のファイル（約 200 バイト）が、カルチャー it-IT でも判定不能（`CodePage = -1`）になった。
`EncodingWebName` は空で、UTF.Unknown の信頼度が採用の下限（0.5）に届かなかった経路である。

| 入力 | 結果 |
|---|---|
| 元のファイル（約 200 バイト。アクセント付き文字の一覧の行、記号・数字の行を含む） | -1 |
| 上から一覧の行と記号・数字の行を除いたもの（約 110 バイト） | 28591（iso-8859-1）。0x80〜0x9F を含まないので正しい |
| さらに `Prezzo: 1.234,56 € — .` の行を足したもの | 1252（windows-1252）。正しい |

**判定の成否は長さよりも内容に左右される。** 1.1.0 仕様書 4.4 節の「短文での既知の限界」は「概ね 90 バイト以下」「約 170 バイト以上の文では救済される」と書いており、
200 バイトなら判定できるように読めるが、170 バイトの記述は上書き経路の話であり、判定不能の経路には当てはまらない。

### 4.2 1.1.0 仕様書 4.4 節の修正

- 「短文での既知の限界」の「約 170 バイト以上の文では、上書き経路に入った入力はすべて正しく救済される」が、**上書き経路だけの話である**ことが明確に分かるように直す
- 新しい小節「シングルバイト系の判定の限界（1.2.0）」を設け、次の内容と、4.1 の表を書く

> シングルバイト系（windows-1252、ISO-8859 など）は、バイト列の構造からは判別できず、文章の統計で推定している。
> そのため、判定の成否は長さよりも内容に左右される。文字の一覧、記号・数字の多い行、その言語で通常使わない文字を含むテキストでは、
> 数百バイトあっても判定できない（`CodePage = -1`）ことがある。その場合は `-Encoding` / `-SourceEncoding` でコードページを明示すること。

- 改善の検討は `docs/EncodingProbe-課題-カルチャーによるシングルバイトの推定.md` にあることを参照として書く

### 4.3 ヘルプ（MAML）

判定を行う次の 6 コマンドのヘルプの NOTES に、4.2 の引用の趣旨を 5 言語で追記する（香港・マカオは台湾と同じ文面。配布物のコピー 14 か所すべてに反映）。

- `Resolve-Encoding`、`Get-ProbedContent`、`Set-ProbedContent`、`Add-ProbedContent`、`Out-ProbedFile`、`Convert-ProbedContent`

コマンドごとに、明示指定に使うパラメータ名を合わせること（`Convert-ProbedContent` は `-SourceEncoding`、`Resolve-Encoding` は明示指定の手段が無いので「読み書きのコマンドで `-Encoding` を指定する」など）。

### 4.4 README

クラスライブラリの README（NuGet の説明に使われるもの）に、同じ趣旨を追記する。PowerShell モジュール側に README があればそちらにも。
